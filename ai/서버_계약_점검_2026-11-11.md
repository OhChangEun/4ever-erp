# 서버 계약 점검 (2026-11-11)

화면이 실서버와 어긋나는 곳을 도메인별로 찾았다(우선순위 1). 백엔드 사본(`~/dev/_team-be-readonly/_4EVER_BE_GW`)은 게이트웨이뿐이라 업스트림 서비스 코드가 없다.

## 근거 규칙

1. 게이트웨이 DTO 는 컨트롤러가 실제로 받거나(`@RequestBody Dto`) 돌려줄 때(`ApiResponse<Dto>`)만 근거로 쓴다. `Map` 이나 `Object` 로 그대로 넘기는 경로는 DTO 와 Swagger 예시가 근거가 아니다.
2. git 이력에 실서버 테스트 커밋이 있으면 그쪽이 DTO 나 예시보다 강하다(영업 담당자 키 사례, 커밋 2e17263).
3. `@RequestParam(name=...)` 이름은 강제다. 이름이 다르면 Spring 이 조용히 버린다.

## 게이트웨이에 없는 경로(시각화 카드에서 계약을 먼저 정한 것, verified=false)

근태 잔디 `attendance/daily-summary`, 재무 현황 `analytics/monthly`, `analytics/ar-aging`, 대시보드 자재 흐름 `dashboard/supply-flow`, 재고 추이 `items/{itemId}/stock-history`. 실서버에서는 404 로 오류 상자가 보인다(실패를 숨기지는 않는다). 백엔드에 같은 계약으로 만들지, 화면에서 뺄지는 팀 결정.

## 확인 불가(응답이 Object 로 넘어감)

응답 필드 모양과 null 여부 대부분. 위험이 큰 것: 공급업체 분류 enum 에 `ITEM` 이 올 수 있음(Swagger), 구매요청 상세 `itemId` 가 숫자로 검증됨, 창고 담당자 전화 필드 이름 두 가지. 응답 검증의 null 요구는 카드 D 에서 예전 화면 가드 수준으로 되돌렸다.
