# React / TypeScript Anti-Pattern Rules

2026-11-09 도입. 새로 쓰는 코드와 리뷰의 기준이다. 규칙 본문(1~7절)은 사용자가 준 원문 그대로이고, 맨 아래 "이 레포에서 어떻게 강제하나" 표만 추가했다. 원문은 고치지 않는다. 바꿀 일이 있으면 표만 고친다.

`review` 트리거와 erp-loop 의 리뷰 단계는 이 문서를 Codex 에 같이 준다. 지적은 "규칙 ID + 위치 + 실제로 생기는 문제 + 가장 단순한 대체"로 적는다.

## 기본 원칙

- React 공식 권장 패턴과 TypeScript의 타입 안정성을 우선한다.
- 동작하는 코드라도 상태 불일치, 불필요한 렌더링, 높은 결합도, 숨겨진 부작용을 유발하는 구현을 금지한다.
- 기존 코드에 안티패턴이 존재하더라도 새로운 코드에 복제하지 않는다.
- 규칙을 준수하기 위해 불필요한 추상화나 과도한 컴포넌트 분리를 하지 않는다.
- 예외가 필요한 경우 근거를 명시하고, 가능한 대안을 먼저 검토한다.

## 1. React 상태 관리

### R01. Derived State 중복 저장 금지

- props 또는 기존 state에서 계산 가능한 값을 별도 state로 저장하지 않는다.
- 단순 계산은 렌더링 중 수행한다.
- 비용이 큰 계산은 필요할 때만 `useMemo`를 검토한다.
- 독립적인 사용자 편집 상태는 예외로 허용한다.

### R02. 불필요한 useEffect 금지

- 단순 데이터 가공, 필터링, 정렬을 위해 `useEffect`와 `setState`를 조합하지 않는다.
- 이벤트 핸들러에서 처리할 수 있는 로직을 Effect로 옮기지 않는다.
- Effect는 외부 시스템과의 동기화가 필요할 때 사용한다.

### R03. State 직접 변경 금지

- 배열의 `push`, `splice` 또는 객체 속성 직접 변경으로 React state를 수정하지 않는다.
- 불변 업데이트를 사용한다.
- 중첩 상태는 가능한 한 평탄한 구조로 설계한다.

### R04. 불필요한 전역 상태 금지

- 단일 컴포넌트에서 사용하는 상태를 전역으로 관리하지 않는다.
- 여러 컴포넌트가 공유한다는 이유만으로 전역 상태를 도입하지 않는다.
- 상태 끌어올리기와 Composition을 먼저 검토한다.
- 서버 상태와 클라이언트 UI 상태를 구분한다.

### R05. 중복된 상태 출처 금지

- 동일한 데이터를 props, Context, 전역 스토어, Query Cache에 중복 저장하지 않는다.
- 데이터의 소유자와 갱신 경로를 명확하게 정의한다.
- 독립적인 편집 초안이나 스냅샷은 예외로 허용한다.

## 2. 컴포넌트 설계

### R06. 과도한 책임 집중 금지

- 하나의 컴포넌트에 독립적인 여러 비즈니스 책임을 집중시키지 않는다.
- 데이터 조회, 복잡한 데이터 변환, 화면 렌더링, 사용자 상호작용의 분리가 유익한지 검토한다.
- 줄 수만을 기준으로 컴포넌트를 분리하지 않는다.

### R07. 불필요한 Props Drilling 금지

- 사용하지 않는 props를 여러 중간 컴포넌트가 단순 전달하는 구조를 반복하지 않는다.
- Composition과 컴포넌트 배치를 먼저 검토한다.
- Context는 실제로 넓은 범위에서 공유되는 데이터에 사용한다.

### R08. 성급한 공통 컴포넌트 추상화 금지

- 외형이 유사하다는 이유만으로 컴포넌트를 통합하지 않는다.
- 과도한 boolean props와 조건 분기를 가진 범용 컴포넌트를 만들지 않는다.
- 실제로 공통된 책임과 변경 패턴이 확인되면 추상화한다.

### R09. 불안정한 key 사용 금지

- 변경, 정렬, 삽입, 삭제가 가능한 목록에서 배열 index를 key로 사용하지 않는다.
- 렌더링 중 `Math.random()`이나 `Date.now()`로 key를 생성하지 않는다.
- 데이터의 안정적인 고유 식별자를 사용한다.

### R10. 렌더링 중 부작용 금지

- 렌더링 중 API 호출, 외부 상태 변경, DOM 직접 조작을 수행하지 않는다.
- 렌더링 로직은 순수하게 유지한다.
- 필요한 부작용은 이벤트 핸들러 또는 적절한 Effect에서 처리한다.

## 3. Hook과 비동기 처리

### R11. Hook 호출 규칙 위반 금지

- Hook을 조건문, 반복문, 일반 중첩 함수 안에서 호출하지 않는다.
- Hook은 React 컴포넌트 또는 Custom Hook의 최상위에서 호출한다.
- Hook 호출 순서가 렌더링마다 달라지지 않도록 한다.

### R12. Effect 의존성 임의 생략 금지

- 경고를 없애기 위해 `react-hooks/exhaustive-deps`를 무분별하게 비활성화하지 않는다.
- 의존성을 제거해야 한다면 코드 구조를 먼저 수정한다.
- Stale Closure가 발생하지 않도록 상태 참조와 함수 의존성을 검토한다.

### R13. 비동기 Race Condition 방치 금지

- 이전 요청의 응답이 최신 화면 상태를 덮어쓰는 상황을 방치하지 않는다.
- 필요할 때 `AbortController`, 요청 식별 또는 데이터 캐시 라이브러리를 사용한다.
- 언마운트 및 요청 조건 변경 시 정리 동작을 검토한다.

### R14. 비동기 오류 무시 금지

- 빈 `catch` 블록으로 오류를 숨기지 않는다.
- 로딩, 성공, 실패, 빈 데이터 상태를 구분한다.
- 사용자에게 필요한 오류 피드백과 개발자 진단 정보를 구분한다.

## 4. 서버 상태 및 데이터 관리

### R15. 서버 상태 불필요한 복제 금지

- TanStack Query가 관리하는 데이터를 별도 전역 스토어나 state에 불필요하게 복제하지 않는다.
- Query Cache를 서버 상태의 기본 출처로 사용한다.
- 사용자 편집용 임시 상태는 별도로 관리할 수 있다.

### R16. 임의적인 캐시 무효화 금지

- 데이터 변경 후 관련 없는 모든 쿼리를 무조건 무효화하지 않는다.
- Query Key를 일관되게 설계한다.
- Mutation이 영향을 주는 데이터 범위를 파악하고 필요한 쿼리만 갱신한다.

### R17. 중복 API 요청 로직 금지

- 동일한 서버 리소스에 대해 컴포넌트마다 독립적인 요청 및 캐시 로직을 반복하지 않는다.
- 공통 Query Hook 또는 API 계층을 활용한다.
- 단, 재사용 가치가 없는 단순 요청을 불필요하게 추상화하지 않는다.

## 5. 성능 및 렌더링

### R18. 근거 없는 메모이제이션 금지

- 모든 함수와 계산에 `useCallback`, `useMemo`를 적용하지 않는다.
- `React.memo`를 습관적으로 사용하지 않는다.
- 성능 문제 또는 참조 안정성 요구가 확인된 경우 적용한다.
- React Compiler 사용 여부를 고려한다.

### R19. 불필요한 상위 상태 관리 금지

- 특정 하위 컴포넌트에서만 필요한 상태를 상위 페이지 전체에서 관리하지 않는다.
- 상태 변경이 불필요하게 넓은 렌더링 범위에 영향을 주지 않도록 한다.
- 실제 성능 문제가 있는 경우 Profiler로 검증한다.

### R20. 렌더링 최적화를 위한 가독성 희생 금지

- 측정되지 않은 성능 문제를 해결하기 위해 복잡한 캐싱이나 우회 로직을 추가하지 않는다.
- 성능 최적화는 측정, 개선, 재측정 순서로 수행한다.

## 6. TypeScript 및 유지보수

### R21. 타입 안정성 우회 금지

- `any`, 무분별한 타입 단언(`as`), `@ts-ignore`로 타입 오류를 숨기지 않는다.
- 외부 입력은 필요한 경우 런타임 검증을 수행한다.
- 불가피한 타입 단언은 안전성 근거를 명시한다.

### R22. 불필요한 중복 로직 금지

- 동일한 비즈니스 규칙을 여러 위치에 복제하지 않는다.
- 공통 규칙은 적절한 함수 또는 모듈로 관리한다.
- 단순한 코드 유사성만으로 추상화하지 않는다.

### R23. 매직 넘버와 하드코딩 남용 금지

- 의미를 파악하기 어려운 숫자와 문자열을 코드 곳곳에 반복하지 않는다.
- 도메인 규칙과 설정값은 명확하게 이름을 부여한다.
- 의미가 명백한 단순 상수까지 불필요하게 분리하지 않는다.

### R24. 검증 없는 리팩터링 금지

- 기존 동작을 변경하지 않는 리팩터링에서는 외부 동작과 계약을 유지한다.
- 변경 영향 범위에 맞는 테스트를 수행한다.
- 기존 테스트를 삭제하거나 약화해 변경을 통과시키지 않는다.
- 테스트 실패의 원인을 확인하지 않고 우회하지 않는다.

## 7. AI 코드 생성 및 리뷰 규칙

코드를 생성하거나 수정하기 전에 다음 사항을 확인한다.

1. 기존 상태 또는 props로 계산 가능한 값을 새 state로 만들지 않았는가?
2. 불필요한 Effect 또는 상태 동기화 로직이 존재하는가?
3. 데이터 출처가 중복되거나 소유권이 불분명하지 않은가?
4. 컴포넌트의 책임과 변경 범위가 적절한가?
5. 비동기 요청의 오류 및 경쟁 상태를 고려했는가?
6. 불필요한 추상화나 메모이제이션을 추가하지 않았는가?
7. 타입 안전성을 우회하지 않았는가?
8. 기존 기능과 테스트의 동작을 유지하는가?

### 위반 사항 발견 시

- 규칙 ID와 위반 위치를 명시한다.
- 실제 발생 가능한 문제를 설명한다.
- 가장 단순한 대체 구현을 우선한다.
- 기존 코드의 범위 밖에 있는 문제는 임의로 대규모 수정하지 않고 별도 보고한다.

### 최종 원칙

**최소한의 상태, 명확한 데이터 흐름, 적절한 책임 분리, 검증 가능한 동작을 우선한다.**

코드의 줄 수를 줄이거나 추상화를 늘리는 것 자체를 목표로 삼지 않는다.
