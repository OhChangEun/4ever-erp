## 진행자 확인 (조정자가 지정한 일곱 항목)

1. 전역 무효화 규칙.
   - `'detail'` 이 들어간 키는 12개 키 파일 중 7개(sales, hrm, inventory, production, purchase, finance, warehouse)의 `details()` 뿐이고, 모두 `[도메인, 엔터티, 'detail', id]` 모양이다(`grep "'detail'" src` 결과 키 파일 밖은 버튼 라벨 `tc('detail')` 과 `queryClient.ts` 뿐). `'detail'` 이 다른 뜻으로 쓰이는 키는 없다. 다른 도메인 키를 건드리는 경로도 없다. prefix 가 `[도메인, 엔터티]` 라 통계 키(`[도메인, 'stats']`)에 닿지 않는다.
   - 같이 stale 이 되는 상세 아닌 하위 키: 견적 `reviewDetail`(A1), `itemInfoForNew`, BOM `materialInfo`, 교육 프로그램 `dropdown`, `statusDropdown`, `categoryDropdown`, 직급 `dropdown`. 무효화는 떠 있는 쿼리만 다시 부르므로 비용은 그 화면이 열려 있을 때 요청 한 번이다. 재고 `history` 는 `detail(itemId)` 아래라 predicate 가 빼서 그대로다. 직급(`positionKeys`)은 같은 엔터티 아래 목록 키가 없어 404 가 나도 다시 받을 목록이 없다(직급 목록 쿼리 키가 다른 곳에 있음, 카드 별도 보고 5).
   - 사용자 값이 키의 맨 위 배열에 문자열로 들어가는 곳(`positionKeys.dropdown(departmentId)`, `departmentKeys.memberDropdown`, `bomKeys.materialInfo(itemId)`, `mpsKeys.list(bomId, …)`)은 그 id 가 글자 그대로 `'detail'` 이고 그 쿼리가 404 일 때만 잘못 잡힌다. 실제 id 모양(`pos-001`, `bom-001`)으로는 일어나지 않는다.
   - 무한 반복과 요청 폭주는 없다. `shouldRetry`(`queryClient.ts:19-22`)가 network, server 만 재시도해 404 는 한 번에 끝난다. 상세 쿼리는 모달 안에만 있어(`grep "Keys.detail("` 결과 상세 쿼리를 쓰는 18곳이 모두 모달) 목록을 다시 받아도 상세가 다시 불리지 않는다. 상세가 다시 불리는 것은 포커스 refetch(오류 쿼리는 stale) 와 모달 재오픈뿐이라 사용자 동작 한 번에 목록 요청 한 번이다.
   - 낙관적 업데이트와의 겹침: 재고 안전재고와 재고 이동(`inventory.mutations.ts:123-150`, `STOCK_OPTIMISTIC_SCOPE`)이 `inventoryKeys.lists()` 를 낙관적으로 고친 사이에 다른 재고 상세가 404 를 받으면, 목록 refetch 가 서버의 옛 값으로 낙관적 값을 잠깐 덮는다. 끝나면 `onSettled` 의 무효화(`useInvalidatingMutation.ts:166-174`, 진행 중 refetch 는 취소하고 새로 받음)가 서버 값으로 맞춘다. 실패하면 스냅샷 복구 뒤 같은 무효화다. 최종 값은 맞고 깜빡임만 있다. 포커스 refetch 와 같은 동작이고, 재고 상세 모달 두 개를 같이 띄우는 경로라 실제로는 거의 없다.
   - 위치 판단: 전역에 둔 것이 맞다고 본다. 19개 상세 모달마다 onError 를 붙이면 빠뜨리기 쉽고, 401 처리와 같은 곳이라 찾기 쉽다. 다만 지금은 "`'detail'` 앞까지가 엔터티" 라는 키 관례에 기대는데 그 관례를 지키는지 보는 검사가 없다. A1 의 대체(쿼리 `meta` 로 다시 받을 목록을 적기)로 가면 관례 의존이 없어지고 `reviewDetail` 도 같이 풀린다. 관례를 유지하려면 키 팩토리 전부를 돌며 `'detail'` 이 `details()` 의 셋째 칸에만 나오는지 보는 테스트를 하나 둔다(추가 관찰 1).
2. 404 판정 필드. `AppError.kind === 'notFound'` 이고, `kind` 는 HTTP 상태(`error.response.status`, `AppError.ts:64, 75`)로만 정해진다. 본문의 `status` 는 보지 않는다. 게이트웨이 사본(`_4EVER_BE_GW` 7dd1211)을 보면 영업, 재무, 인사 9개는 업스트림이 HTTP 4xx 를 주면 `WebClientResponseException` 을 잡아 `ResponseEntity.status(sc).body(ApiResponse.fail(...))` 로 HTTP 상태를 그대로 준다(`SdHttpServiceImpl.java:704-715`). 그래서 HTTP 404 로 잡힌다. 업스트림이 HTTP 200 에 본문 `success: false, status: 404` 를 주면 `retrieve()` 가 예외를 안 내고 `ResponseEntity.ok(response)`(`SdHttpServiceImpl.java:364`)로 HTTP 200 이 된다. 이때 FE 는 `axiosInstance.ts:37-40` 에서 `invalidShape` 로 올려 오류는 보이지만 목록을 다시 받지 않는다. SCM 10개는 업스트림 상태를 그대로 넘겨 같은 조건이다. 업스트림이 어느 쪽인지 사본에 없다(verified=false). 이 diff 의 결함은 아니고, ARCHITECTURE 10절의 새 verified=false 행에 "HTTP 200 + 본문 404 면 목록을 다시 받지 않는다" 를 한 줄 더하면 된다(추가 관찰 2).
3. 목의 "목록에 있다" 기준. 19개 모두 필터와 페이지를 걸지 않은 그 로그인의 전체 목록 함수로 찾는다(`quotesOf`, `ordersOf`, `customersOf` `sales.handlers.ts:173-216`, `requisitionsOf` `purchase.handlers.ts:141`, `programsOf`, `warehousesOf`, BOM `createdBoms` + 기본 BOM, MES `mes-001`~`mes-050`). 다른 상태라서 필터 밖인 행이 404 가 되는 곳은 없다. 예외는 의도된 둘이다. 출고 준비는 배송을 시작한 행이 목록에서 빠지므로 `readyToShipOf` 로 보고 404(카드 결정 3), 재고 품목은 일반 목록보다 넓은 품목표(`catalogItem`, 창고 3D 패널이 여는 14개 포함)로 본다. 화면이 목록 밖 경로로 상세를 여는 곳(창고 3D `WarehouseStockPanel.tsx:95` → 재고 상세, 교육 지정 모달 → 교육 현황 `emp-001`)도 목 목록 안의 id 다. 50건 상한으로 밀려난 행의 404 는 완료 기준 3 이 정한 의도이고, 화면 목록에서도 이미 안 보이는 행이다.
4. 계약. 404 를 단 19개 경로는 `DETAIL_PAIRS`(`src/test/contract/detailPairs.ts`)와 같고, 테스트 "목록과 짝인 상세 GET 19개만 404 를 선언한다" 가 둘을 맞춘다. `/profile`, 통계, 드롭다운은 들어가지 않았다. 제품 상세(`/scm-pp/pp/products/{productId}`)는 목록 `/scm-pp/pp/products` 와 짝이라 맞다. `ApiError` 는 `status`, `success: false`(const), `message` 필수이고 `additionalProperties` 를 막지 않아 게이트웨이의 선택 필드 `errors` 를 받아 준다. `data` 가 없어야 한다는 것은 스키마가 강제하지 않는다(목은 안 보내므로 지금은 문제 없음). 생성 타입 drift 검사는 통과했다.
5. 고친 기존 테스트. 상세 id 를 목록 기본 행 id 로 바꾼 파일들(nullable 4개, guardedReads, QuoteReview, sales.defects, purchase.i18n, state)은 단언을 그대로 두었다. `state.test.ts` 는 `item-9999`(사실상 모터 A 본문) 대신 목록의 다른 품목 `item-1002` 로 바꿔 "다른 품목은 그대로" 를 더 정확히 본다. 약화가 아니다. "쓰기 뒤 GET 전수" 에서 출고 준비 상세를 404 스키마로 보는 것도 정당하다. 배송 시작 쓰기가 유일한 행 so-002 를 목록에서 빼므로 404 가 맞는 응답이다. 그 상세의 200 본문은 쓰기 상태를 읽지 않아(`inventory.handlers.ts:269-280`, 존재 확인만 상태를 본다) 쓰기 전 GET 전수에서 이미 같은 모양을 본다. `applyAllMockWrites` 는 쓰기를 기본 행 id 와 `id-1` 둘 다에 보내서(`src/test/mockApi.ts:258`) 다른 상세의 "쓰기 뒤 200 스키마" 검사 범위는 줄지 않았다.
6. 견적 상세 오류 창 닫기 뒤 빈 견적 틀(₩0). 이 diff 의 회귀가 아니다. `useDismissibleError` 로 오류 창만 닫는 동작은 이 카드 전부터 500, 네트워크 오류에 똑같이 있었고(`QuoteDetailModal.tsx:27-35` 는 이 diff 에서 안 바뀜), 같은 훅으로 상세를 불러오는 모달 11곳(견적 검토, 주문, 고객, 재고, 출고, 구매 요청, 발주, 전표, 창고 상세와 창고 수정)이 같은 모양이다. 404 가 생기면서 이 경로가 "다른 사용자가 지운 건" 이라는 현실적인 경우에도 나오게 된 것뿐이다. 다만 닫은 뒤 합계 ₩0 과 빈 칸이 실제 값처럼 보여 우선순위 2(실패를 숨기지 않는다)에 걸린다. 진행자 제안 레벨 P2, 이 카드 범위 밖. `useDismissibleError` 를 쓰는 상세 모달 전부를 "오류면 닫기 = 모달 닫기" 로 바꾸는 카드로 따로 가는 쪽을 권한다(MES 가 이번에 한 방식).
7. MES 상세 모달. 로딩 분기(`ProcessDetailModal.tsx:81-89`)는 그대로라 첫 로딩은 예전과 같다. 오류 분기 조건 `isError || !mesDetail` 도 그대로라, mesId 가 비어 쿼리가 꺼진 경우는 예전처럼 오류 표시다(글자만 `ModalStatusBox` 로 바뀜). 오류 뒤 포커스 refetch 중에는 TanStack v5 에서 `isLoading` 이 false, `isError` 가 true 로 남아 오류 상자가 유지되고 로딩으로 깜빡이지 않는다. 닫기는 `ModalProps.onClose` 를 그대로 넘겨 모달 전체를 닫는다(단위 테스트와 e2e 확인). `ModalStatusBox` 가 `role` 과 포커스 이동이 없는 것은 공통 컴포넌트의 기존 상태라 이 diff 의 지적이 아니다.
