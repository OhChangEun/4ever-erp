## 진행자 확인 (조정자가 지정한 일곱 항목)

1. 결정성. 같은 요청에는 같은 응답이다. `new Date()` 를 쓰는 목은 10곳(`grep -n "Date.now()\|new Date(" src/mocks`)이다.
   - 통계 금액(`financeAnalytics.handlers.ts:16-48` `financeMonthlyPoints`, `monthlyMetric`)은 날짜를 달 이름(`month`)에만 쓰고 값은 달 순번 `i` 로 정한다. 그래서 i18n 테스트의 정확값(₩186,670,000 = 800,000,000 × 7/30 반올림, ₩142,800,000 = 612,000,000 × 7/30)은 달, 연이 바뀌어도 같다. 직접 계산해 맞췄다.
   - 통계 증감과 추이(`src/mocks/utils.ts:43-54` `periodStat`)는 지표 이름과 기간의 해시라 날짜와 무관하다.
   - 매출 분석(`sales.handlers.ts:245-258`)은 주 월요일 날짜의 해시로 값을 정한다. 기간을 주면 결정적이다. 기간이 없으면 끝이 오늘(UTC, `dateKey` 가 `toISOString`)이라 날마다 바뀐다. 화면 테스트는 `server.use` 로 고정했고 `realism.test.ts:539-554` 는 기간을 상수로 준다(연말 걸친 2025-12-29 ~ 2026-01-04 포함). 한국 시각 0~9시에는 기본 끝이 어제가 된다. 화면이 늘 기간을 보내면 영향 없다.
   - 오늘 기준 상대 날짜(MES 계획일 `production.handlers.ts:310`, 재고 추이 `stockHistory.handlers.ts:19`, 근태, 자재 흐름)는 이번 카드 전부터 있던 방식이다. 값의 모양은 날짜와 무관하다. 다만 `realism.test.ts:358` 은 MES 목록 행과 상세의 계획일을 따로 요청해 비교해서, 자정을 끼고 돌면 하루 어긋날 수 있다(아래 추가 관찰 3).
   - 시계를 고정하는 테스트(`vi.useFakeTimers`, `setSystemTime`)는 이번 diff 에 없다. 위 이유로 필요한 곳은 없다고 본다.
2. 목 상태 저장소. 쓰기 결과는 새 씨앗 위에 그대로 덮인다(`quotesOf` `sales.handlers.ts:161-165` 가 `quoteStatus` 를 덮고, MES 는 `mesRow` `production.handlers.ts:304` 가 상태와 공정을 `mesId` 로 읽는다). 생성 행의 상세도 그 행에서 만든다(`realism.test.ts` 새 행 테스트 통과). 예외는 A2, A3. 통계 건수는 씨앗 길이(`flow(mockQuotes.length)` `sales.handlers.ts:336`, `flow(mockOrders.length)` `:330`)라 생성 뒤 목록과 1건씩 어긋난다. 앞 카드 "목이 쓰기 결과를 따르게" 별도 보고 9의 조정자 결정(통계는 쓰기를 따르지 않는다)과 같은 동작이라 허용 범위다. 다만 1,200 일 때는 안 보이던 차이가 이제 4건 대 5건으로 보인다(추가 관찰 1).
3. 계약 일치. 계약 테스트(쓰기 전후 GET 전부)가 통과한다(Codex, 진행자 둘 다). 비율 합은 `split(100, [5,3,2])` 가 나머지를 첫 칸에 몰아 늘 정확히 100(50, 30, 20)이고, 금액 합도 같은 `split` 이라 99/101 이 될 수 없다. 금액은 1만 원 단위 반올림이라 정수다. 순이익은 다섯째 달만 적자이고, 통계에 쓰는 이번 달, 최근 3달, 12달 합은 모두 양수다. 값 0 이면 `delta_rate` 0, 추이 전부 0 이다. 건수 1 이면 첫 점도 1 로 반올림되어 `delta_rate` 0 이다.
4. 없는 id 에 200. 게이트웨이 사본은 견적 상세를 업스트림으로 그대로 넘기고(`SdHttpServiceImpl.java:351-371`), 업스트림이 4xx 를 주면 그 상태 코드 그대로 `ApiResponse.fail("견적 상세 조회 중 오류가 발생했습니다.", status, null)` 를 돌려준다(`SdHttpServiceImpl.java:704-715`). 실패 모양은 `{ status, success: false, message, errors? }`(`ApiResponse.java:15-41`, `data` 는 null 이라 빠진다). 게이트웨이에는 `QUOTATION_NOT_FOUND(1022, 404)`, `ORDER_NOT_FOUND`, `CUSTOMER_NOT_FOUND`, `PURCHASE_ORDER_NOT_FOUND` 등 404 코드가 있고(`ErrorCode.java:24-100`), 예외 처리기가 404 로 답한다(`GlobalExceptionHandler.java:36-71`). 업스트림이 실제로 404 를 던지는지는 사본에 없어 확정하지 못한다. 그래도 서버가 없는 건을 200 과 다른 건의 본문으로 줄 근거는 없다. 판단: 목이 200 을 주면 화면은 없는 건을 정상처럼 보여 우선순위 2(실패를 숨기지 않는다)와 부딪친다. 다만 이번 카드에서는 조정자 지시(완료 기준 3)이고, 목록에서 고른 id 만 상세를 부르는 화면에서 이 경로는 알림 링크나 오래된 링크 정도다. 이 카드 범위에서는 지시대로 두고, 계약에 404 를 더한 뒤 목을 404 로 바꾸는 카드를 따로 여는 쪽을 권한다(카드 별도 보고 3 과 같은 방향).
5. 증감률 `delta_rate`. 결론: 실서버가 퍼센트(12.0)를 준다는 근거는 사본 어디에도 없다. 그래서 "목을 퍼센트로 맞추기"는 근거가 없다. 그런데 비율이라는 것도 확정이 안 된다. 대시보드는 오히려 "절대 차이"라는 근거가 있다.
   - 게이트웨이는 `delta_rate` 를 계산하지 않는다. 비주석 코드는 DTO 필드 선언뿐이다(`StatisticsValueDto.java:15-16` Double, `StatisticValueDto.java:15-16`, `FcmStatisticsValueDto.java:15-16`, `scm/PeriodStatDto.java:17-18` BigDecimal). 값은 업스트림(business, scm 서비스)이 만들고 사본에 없다. 대시보드 통계는 `ApiResponse<?>` 로 받아 캐스팅만 하는 Map 프록시다(`DashboardHttpServiceImpl.java:33-42`). 그래서 DTO 가 강제력이 없다.
   - 대시보드 DTO 주석은 "Absolute difference from previous period (not percentage). 1000 이고 전이 900 이면 delta 는 100"이다(`dashboard/dto/response/DashboardValueDto.java:23-29`).
   - FE 이력: 팀 프로젝트 때(실서버 연동 중) `adbe61c8`(2025-10-31) 이 `createStatCard` 표시를 `(delta * 100).toFixed(1)%` 에서 `${delta}${unit}`(예: "+100₩", "+3명")으로 바꿨다. 절대 차이 해석과 맞는다. 커밋 제목은 "직급 관리 탭 삭제"라 의도를 적은 커밋은 아니다. 그 뒤 리팩토링 때 `1dbbdfed`(2026-10-27) 가 실서버 없이 `${delta}%` 로 바꿨다. 지금 화면(`src/lib/CreateStatCard.ts:16`)은 비율로 봐도 절대 차이로 봐도 틀린 표시다.
   - 비율 쪽 근거는 게이트웨이 옛 목(주석 처리된 `ImController.java:498-529`, `PpController.java:97-126` 의 0.082 등, `MmController.java:58` Swagger 예시 0.1044 등)뿐이다. 실서버 응답이 아니다.
   - 권하는 처리: 목은 지금처럼 계약(비율)대로 두고 퍼센트로 바꾸지 않는다. 화면 표시는 실서버 형태를 팀에 확인한 뒤 고친다(비율이면 `× 100`, 절대 차이면 단위를 붙인 차이). `ai/decisions.md` 에 verified=false 팀 확인 항목으로 남길 일이다. 이 diff 의 지적은 아니다(수정 전 목도 0.12 를 줬다).
