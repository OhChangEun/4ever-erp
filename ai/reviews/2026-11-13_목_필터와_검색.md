## 진행자 확인 (조정자가 지정한 여섯 항목)

1. `filterBy` 위치와 404.
   - `filterBy(` 호출 19곳(`grep`, finance 2, production 4, purchase 3, sales 3, inventory 3, hrm 5)이 모두 목록 핸들러 안에서 `paged(request, filterBy(request, <목록>, <규칙>))` 모양이다. 넘기는 목록은 쓰기 상태를 덮은 함수 결과(`requisitionsOf`, `purchaseOrdersOf`, 공급사 `editedSupplier` 덮은 content, `quotesOf`, `ordersOf`, `customersOf`, `mesListOf`, 계획 주문의 전환 상태 map, 직원의 수정 덮기)라 쓰기 뒤, 쪽 자르기 전이다. `paged` 는 받은 배열 길이로 `makePage` 를 만들어 `totalElements`, `totalPages` 가 거른 수다(`src/mocks/utils.ts:82-90`). 테스트 "필터를 고르면 쪽은 거른 행에서 자른다" 와 52행 표가 총 건수를 본다.
   - 404 는 그대로다. `filterBy` 는 목록 핸들러 안에서만 부르고 `requisitionsOf` 같은 공용 함수는 바뀌지 않아, 상세의 "목록에 있는가" 판정은 필터 전 전체 목록 기준이다. MES 상세도 목록과 같은 `mesRow` 를 쓴다(`production.handlers.ts:450`, `:866`). `realism.test.ts`, 계약 테스트 통과.
   - 예전에 쪽을 안 자르던 목록(재고, 안전재고, 입고 완료, 전표 2, 인사 한 줄 목록 4)이 이번에 `paged` 로 바뀌었다. 화면 호출은 모두 page, size 를 보내거나(안전재고와 재고는 page 0 이면 빼서 기본 0) 행이 1개라 잘리는 행이 없다.
2. 화면 다섯 곳의 `'with-all'`.
   - 처음 화면은 예전과 같다. 다섯 곳 모두 선택 상태의 처음 값이 이미 `''` 였다(`PurchaseRequestListTab.tsx:67` 등). 예전 첫 값이 특정 상태였던 곳은 없다. `''` 이면 `Dropdown` 이 placeholder("전체 상태", "전체 카테고리")를 보인다(`packages/ui/src/Dropdown.tsx:71`).
   - 보내는 값. 구매 세 화면은 `getParsed(..., { params })` 로 axios 에 객체를 넘기고, axios 는 null, undefined 만 빼서 `''` 는 `statusCode=` 로 나간다(`paramsSerializer` 없음). 게이트웨이 `@RequestParam(defaultValue = "ALL")`(`MmController.java:43`, `:45`, `:230`, `:414`)은 Spring 규칙상 빈 문자열이면 기본값을 쓰므로 ALL 이다. 출퇴근은 `HrmController.java:508` `required = false` 라 `""` 그대로 가고 서버 처리는 사본으로 모른다(verified=false). 다만 처음 화면이 예전부터 `''` 를 보냈으므로 새 위험은 아니다.
   - 쿼리 키. 목록 키는 params 객체 그대로다. "전체" 를 다시 고르면 처음 화면과 같은 키라 캐시를 다시 쓴다.
   - 1쪽 이동. 다섯 드롭다운 `onChange` 가 모두 `setCurrentPage(1)` 을 그대로 부른다(`PurchaseRequestListTab.tsx:234`, `PurchaseOrderListTab.tsx:162`, `SupplierListTab.tsx:180`, `:189`, `AttendanceTab.tsx:163`).

3. `attendanceKeys.statusDropdown` 삭제. 남은 참조는 카드뿐이다(`grep`). 무효화하던 곳도 없었다(출결 mutation 이 `attendanceKeys.all` 을 무효화했다면 예전엔 상태 드롭다운도 같이 다시 받았지만 값이 고정이라 차이 없음). 새 키 `dropdownKeys.options('attendanceStatusDropdown')` 은 이 화면 하나만 쓴다. 공급사 분류와 상태 키는 `SupplierFormModal.tsx:53`, `:59` 와 같은 키, 같은 fetch 함수를 쓰고 모드(`without-all`)는 `useMemo` 안에서만 적용돼 캐시를 같이 써도 옵션이 섞이지 않는다.
4. 검색. `filterBy` 는 `String.prototype.includes` 만 쓴다(`src/mocks/utils.ts:127`). `RegExp` 가 없어 `(`, `*`, `\` 같은 글자도 그대로 부분 일치로 찾고 ReDoS 경로도 없다. 검색어와 필터 값은 `trim()` 뒤 `toLowerCase()`. 한글은 대소문자 변환에 영향이 없다. 검색 타입이 `''` 이거나 규칙에 없는 값이면 `Object.hasOwn` 이 거짓이라 그 목록의 모든 검색 칸을 본다(verified=false, 카드 결정 2). 재고 목록만 예외로, 검색어가 창고 이름과 똑같으면 일반 재고 행이 아니라 창고 재고 14행을 준다(카드 결정 7). 이 비교는 `trim()` 전의 검색어를 써서 앞뒤 공백이 있으면 일반 행 쪽으로 간다(`inventory.handlers.ts:139-142`). 창고 3D 패널은 목록의 이름을 그대로 보내 실제로 걸리지 않는다. 진행자 관찰 2.
