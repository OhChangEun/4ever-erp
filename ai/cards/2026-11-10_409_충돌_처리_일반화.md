# 409 충돌 처리 일반화

- 출처: 아키텍처 계획 5절 2번(낙관적 락 일반화)
- 우선순위: 1 서버와 일치
- 브랜치: refac/409_충돌_처리_일반화
- 크기: 반나절

## 현상

1. 409(다른 사용자가 먼저 수정)를 다루는 곳은 BOM 상태 변경 하나뿐이다(`BomDetailModal.tsx:41`). 나머지 mutation 은 409 를 받으면 오류 토스트만 띄우고 화면은 옛 데이터를 그대로 둔다. 사용자가 다시 눌러도 같은 옛 값 위에서 또 거부된다.
2. BOM 의 충돌 창은 모달 안에 직접 그린 마크업이다(`BomDetailModal.tsx:108`). `role`, `aria-modal`, 제목 연결이 없어 화면 읽기 프로그램이 대화상자로 알리지 않는다.

## 완료 기준

1. 공통 빌더가 409(`AppError.kind === 'conflict'`)를 받으면 그 mutation 의 무효화 키를 다시 가져온다. 다른 오류는 지금처럼 무효화하지 않는다. 낙관적 mutation 은 지금도 정산 때 무효화하므로 그대로.
2. 공통 `ConflictDialog`(`src/app/components/common/ConflictDialog.tsx`): `role="alertdialog"`, `aria-modal`, 제목과 설명 연결, "닫기"와 "최신 데이터 불러오기". BOM 이 이걸 쓴다.
3. 기존 BOM 409 e2e 그대로 통과.
4. 단위 테스트: 빌더 409 → 무효화, 500 → 무효화 안 함. ConflictDialog 역할과 버튼.

## 결정 (AI 가 정함, 사용자 2026-11-10 "끝까지 진행")

1. 다른 엔티티에 version 을 보내는 일은 하지 않는다. 서버 계약(어느 리소스가 version 을 받는지)이 없다. OpenAPI 계약 카드에서 정한다. 이 카드는 "409 를 받았을 때 화면을 서버에 맞추는 것"까지.
2. 409 를 받으면 자동으로 다시 가져온다(다이얼로그의 버튼을 기다리지 않는다). 옛 값 위에서 재시도하는 것을 막는 게 우선순위 1 이다. BOM 다이얼로그의 "최신 데이터 불러오기"는 상세를 한 번 더 가져오고 닫는다.
