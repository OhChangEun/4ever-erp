# 영업 매출 분석 실패

- 출처: 영업 서버 계약 2 카드의 "별도 보고" 4(고객 등록 응답)와 5(매출 분석 실패 숨김). 이 카드의 첫 별도 보고 셋(고객 등록 안쪽 실패, 고객 수정 담당자 키, 매출 분석 로딩)은 코디네이터 지시로 같은 카드에서 다뤘다(담당자 키는 리뷰 뒤 되돌림).
- 구현: Claude(erp-dev)
- 우선순위: 2 입력 보존과 실패 노출(매출 분석, 고객 등록 안쪽 실패), 1 서버와 일치(고객 등록 응답)
- 브랜치: fix/sales3
- 결정할 것: 전부 AI 가 정했다. `ai/decisions.md` 2026-11-11 "카드 영업 매출 분석 실패 (AI 결정)" 한 행.

## 근거

- 매출 분석: `SalesChart.tsx` 가 `useQuery` 의 `data` 만 꺼냈다. 조회가 실패하거나(500) 형식 검사(`salesAnalysisSchema`)가 막으면 `analyticsData` 가 없어 세 칸 모두 "데이터가 없습니다" 빈 문구를 보였다. 로딩 중에도 같은 빈 문구였다. 로딩, 실패, 빈 기간이 같은 화면이었다.
- 고객 등록: 게이트웨이 `business/controller/SdController.java:204-262` 의 `POST /customers` 는 `sdService.createCustomer`(`business/impl/SdServiceImpl.java:28`)를 부르고 `ApiResponse<CreateAuthUserResultDto>` 를 돌려준다. 봉투는 한 겹이고 data 는 `business/dto/hrm/CreateAuthUserResultDto.java:8-12` 의 eventId, transactionId, success, userId, failureReason 이다. 게이트웨이 ObjectMapper(`config/application/AppConfig.java:13`)는 null 을 빼지 않아 문자열 필드는 null 로 올 수 있다(`ApiResponse` 의 NON_NULL 은 바깥 봉투에만, 그래서 업스트림 data 가 null 이면 data 키가 빠진다). `SdServiceImpl.java:54` 는 바깥 success 만 본다.
- 지난 카드가 본 `business/dto/customer/CustomerCreateResponseDto.java` 와 `SdHttpServiceImpl.java:135` 는 이 경로에서 쓰지 않는다(컨트롤러가 부르지 않음).
- 화면 계약은 `data: ServerResponse` 였고 `ServerResponse` 가 다시 봉투(`status, success, message, data`)였다. 안쪽 data 는 숫자 customerId, customerCode, companyName 등 고객 필드 17개. MSW 목도 같은 이중 봉투였다.
- 고객 수정 담당자 키: 화면은 name, mobile, email 로 보낸다. 게이트웨이 수정 컨트롤러는 본문을 `Map` 으로 받아 그대로 넘긴다(`SdController.java:311`, `SdHttpServiceImpl.java:196`). `CustomerUpdateRequestDto`, `CustomerManagerDto`(managerName 등)는 게이트웨이 안에서 참조가 0건인 DTO 다. FE 커밋 `2e17263`(2025-11-10 "#136 고객 수정 백엔드 테스트 완료")이 실서버 테스트 뒤 managerName 등에서 name, mobile, email 로 일부러 바꿨다. 그래서 바꾸지 않는다.
- 컨트롤러 Swagger 예시(`SdController.java:309`)는 managerName 등이지만 Map 을 그대로 넘겨 강제력이 없다. 2e17263 실서버 테스트를 우선한다.

## 결과

1. 매출 분석 조회가 실패하면 기간 선택은 남기고 차트 세 칸 대신 `TableStatusBox` 오류 상자 하나를 보인다. 문구 "매출 분석 데이터를 불러오는 중 오류가 발생했습니다." / "Couldn't load sales analytics."(`sales.chart.loadError`), 그 아래 오류 종류 한 줄(`useErrorMessage`), 요청 ID 가 있으면 그 줄. 500 이면 서버 오류, 형식 검사 실패면 형식 오류 줄이 나온다. 데이터를 보인 뒤 다시 받기(창 포커스 등)가 실패해도 오류 상자로 바뀐다. 재시도는 기간을 바꾸거나 창에 돌아올 때 다시 조회(`refetchOnWindowFocus`)하는 것으로, 다른 목록 화면과 같다.
2. 매출 분석 로딩 중에는 같은 자리에 `TableStatusBox` 로딩 상자만 보인다. 문구 "매출 분석 데이터를 불러오는 중입니다..." / "Loading sales analytics..."(`sales.chart.loading`). 빈 문구는 성공 응답이 정말 비었을 때만 나온다. 차트 세 칸은 하위 컴포넌트 `SalesChartPanels`(같은 파일)로 옮겨 성공 응답만 받는다.
3. 고객 등록 응답을 게이트웨이 모양으로 맞췄다. 계약 `POST /business/sd/customers` 의 data 를 `CreateCustomerResponse`(eventId, transactionId, userId, failureReason 은 문자열 또는 null, success 는 boolean)로 바꾸고, data 를 필수에서 뺐고, 이중 봉투 `ServerResponse` 를 지웠다. `openapi.gen.ts` 를 다시 만들었다. `postCustomer` 는 생성 타입 `CreateCustomerEnvelope`(계약 경로의 200 응답)로 받는다. MSW 목은 봉투 한 겹에 같은 모양을 준다. 쓰이지 않게 된 목 타입 `NewCustomerBody`, `ManagerBody` 는 지웠다.
4. 고객 등록 안쪽 success 가 false 면 `postCustomer` 가 `CustomerAccountError`(`AppError` 의 하위 클래스, kind server)로 던진다. 화면은 이 오류에만 쓰는 안내 토스트("고객사는 이미 등록됐을 수 있습니다. 고객 목록을 확인한 뒤 담당자 계정을 확인해 주세요." / "The customer may already be registered. Check the customer list, then check the contact's account.", `sales.newCustomer.accountError`)를 보이고 다시 시도를 권하지 않는다. 모달과 입력은 남는다. 다른 실패는 예전 문구("고객 등록 중 오류가 발생했습니다." + 오류 종류)다. 고객사 행은 이미 저장됐을 수 있어(계정 생성만 실패) `useCreateCustomer` 가 onError 를 감싸 이 오류일 때만 `customerKeys.lists()` 를 무효화한다(같은 고객 중복 등록 방지, verified=false). 다른 실패는 예전처럼 무효화하지 않는다. failureReason 은 개발자용 message 에만 둔다. 바깥이 성공인데 data 가 빠지면 성공으로 둔다. 그래서 응답 타입은 `CreateCustomerResponse | undefined`.
5. 고객 수정 담당자 키는 이 카드 전과 같다(name, mobile, email). 한 번 managerName 등으로 바꿨다가 리뷰 뒤 되돌렸다. 지금 동작을 고정하는 테스트를 남겼다.
6. 응답 런타임 검증(zod)은 더하지 않았다. 화면은 응답에서 안쪽 success 하나만 읽고, 다른 필드는 쓰지 않아서 검증은 새 실패 경로만 만든다.
