# 성능 3: 탭 표를 도메인별로, 차트는 열 때 받기

- 출처: 계획 9절 2번(무거운 라이브러리 dynamic import), 기준선의 "재무, 영업, 재고가 recharts 121.6KB 를 첫 로드에 받는다"
- 우선순위: 3 빠르게 느껴진다, 4 import 방향(도메인끼리 import 금지, 계획 4-2)
- 브랜치: refac/성능_3_차트_지연_로드
- 크기: 한두 시간

## 현상

1. 탭 정의가 공용 파일 하나(`src/app/types/componentConstant.ts`)에 있고, 재무, 영업, 재고 탭 컴포넌트를 모두 import 한다. 재무 화면이 영업 탭(차트 포함)과 재고 탭 코드를 같이 받는다.
2. recharts 는 영업의 매출 분석 탭 하나만 쓰는데 세 화면이 첫 로드에 받는다.

## 완료 기준

1. 탭 표를 `finance.tabs.ts`, `sales.tabs.ts`, `inventory.tabs.ts` 로 나눈다(구매는 이미 `purchase.tabs.ts`). 공용 파일 삭제.
2. 매출 분석 탭은 `next/dynamic` 으로 탭을 열 때 받는다. e2e 로 열 때 청크를 받고 차트가 그려지는지 본다.
3. 첫 로드 JS 와 화면 수치 전후. 테스트, 빌드, e2e 통과.

## 결정

없음.

## 결과

1. 첫 로드 JS(gzip): 재무 503.7 → 286.3KB(-43%), 영업 503.6 → 382.9, 재고 503.5 → 381.7. 기준선 대비 재무는 574.3 → 286.3(절반).
2. 화면(CPU 4배): 스크립트 전송 구매, 영업 586 → 480KB, 재고 609 → 505KB. 재고 긴 작업 109 → 76ms.
3. e2e 1개 추가(매출 분석 탭을 열면 청크를 더 받고 차트가 보인다). 그 과정에서 e2e 헬퍼 `visibleAlerts` 가 Next 라우트 안내 요소(클라이언트 이동 뒤 페이지 제목을 읽음)를 오류로 세던 것을 고쳤다.
4. 성능 2 카드 결과의 잘못을 바로잡는다: `SalesChart` 는 공용 `formatDate` 가 아니라 같은 이름의 지역 함수(`toISOString`)를 써서 기본 기간이 여전히 하루 밀렸다. 이 카드에서 `toDateKey` 로 고쳤다. 같은 패턴(`toISOString().split('T')[0]` 로 "오늘"을 만듦) 6곳(견적일, 보고서 파일명, 출결 오늘, MPS 기준일, 구매 요청일)도 고치고, ESLint `no-restricted-syntax`(error)로 막았다. `grep -rn "toISOString().split" src` 0건.
