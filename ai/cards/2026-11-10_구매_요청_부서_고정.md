# 구매 요청 부서 고정

- 출처: i18n 5 결과 3
- 구현: Codex(ultra), 리뷰: Claude(역할 교대)

- 출처: i18n 5 구매 결과 3
- 우선순위: 1(로그인 사용자와 다른 부서 표시 및 고정 요청자), 2(조회 실패 표시와 입력 보존)

## 결정할 것

없음. 카드에서 허용한 부서 없는 사용자 제출 차단을 적용했다. 확인되지 않은 부서를 추정해 보내지 않기 위해서다.

## 결과

1. 요청 부서는 번역 메시지의 "생산팀" 고정값이었다. 인증 사용자 프로필을 조회하는 기존 `getProfile`, `profileKeys.info()`로 바꾸고 서버 부서명을 번역 없이 표시한다. 모달을 열 때 다시 조회하고 완료 전에는 캐시의 부서를 표시하거나 제출하지 않는다.
2. 기준은 팀 백엔드 읽기 전용 사본이다. `_4EVER_BE_GW`의 `PurchaseRequisitionCreateRequestDto`는 `items`만 받으며 `MmController.createPurchaseRequisition`이 인증 principal의 userId를 `requestId` 쿼리로 전달한다. 프런트의 `requesterId: '1234'`를 제거하고 OpenAPI와 생성 타입도 맞췄다. 부서 ID나 이름을 요청 본문에 추가하지 않았다. 하위 SCM 서버가 부서를 결정하는 방식까지는 확인되지 않았다.
3. `ProfileController.getEmployeeProfile`은 인증 사용자 유형별 프로필을 원형 중계한다. 인접한 직원 DTO의 `department` 문자열을 참고하되 실제 프로필 전체 형식을 확정할 수 없어 `department`, `departmentName` 문자열을 모두 허용한다. 두 형식이 실 서버에서 모두 사용된다고 확인한 것은 아니다.
4. 부서 없음, null, 공백, 잘못된 형식은 안내 후 제출을 차단한다. 조회 중과 조회 실패도 제출할 수 없으며 재시도해도 품목 입력을 유지한다. 새 안내는 ko/en에 함께 추가했다.
5. 회귀 테스트 11개: ko/en 원본 부서명과 두 필드 형식, 품목만 전송, 부서 없는 네 경우, 조회 중 차단, 실패 후 재시도와 입력 보존. 수정 전 기존 10개 전체 실패와 추가 숫자 형식 1개 실패를 각각 확인했다.
6. 검증: `pnpm exec tsc --noEmit -p .` 통과, `pnpm exec eslint .` 오류 0 경고 0, `pnpm exec vitest run` 94개 파일 586개 테스트 통과, `pnpm build` 통과. 빌드 후 루트와 포털의 `next-env.d.ts`를 HEAD 내용으로 원복했다. 독립 리뷰에서 추가 결함은 없었다.
7. 범위 밖: `USER_PROFILE_INFO`는 `/business/hrm/employees/by-internel-user`지만 백엔드 `HrmController`는 뒤에 `/{internelUserId}`를 요구한다. MSW는 ID 없는 경로를 성공 처리한다. 이번 카드에서는 수정하지 않았다.
