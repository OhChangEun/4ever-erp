# 옵저버빌리티 1: 요청 ID, Error Boundary 3층, web-vitals

- 출처: 계획 16-1 "옵저버빌리티: Sentry + web-vitals + request-id", 결정 기록 "옵저버빌리티" 행(Error Boundary 3계층)
- 우선순위: 2(실패를 숨기지 않고, 사용자가 무엇을 보고해야 하는지 안다), 4
- 브랜치: feat/옵저버빌리티_1
- 크기: 1일

## 현상

1. 화면에 오류가 떠도 어느 요청인지 알 수 없다. 프록시 로그와 화면 오류를 잇는 값이 없다.
2. 업스트림 연결이 실패하면 프록시에 처리가 없다. Next 기본 500(본문 없음)이 나간다.
3. 모달 안 컴포넌트가 던지면 화면 전체가 오류 페이지로 바뀐다. 입력 중이던 다른 화면 상태도 같이 잃는다.
4. 루트 오류 화면(`src/app/error.tsx`)이 운영에서도 stack 을 그대로 보여준다.
5. 성능 지표(LCP, INP, CLS)를 실제 사용자에게서 모으는 곳이 없다.

## 완료 기준

1. 프록시가 요청마다 `x-request-id` 를 정한다. 들어온 값이 올바르면(영숫자와 `-`, 8~64자) 쓰고 아니면 새로 만든다. 업스트림 요청과 모든 응답(401, 403, 400 포함)에 싣는다.
2. 업스트림 연결 실패는 502 `{ success: false }` 와 요청 ID. 실패 요청은 서버 로그에 한 줄(JSON: requestId, method, path, status, ms).
3. `AppError` 가 응답 헤더의 요청 ID 를 담는다. `TableStatusBox`, `StatSection` 의 오류 줄에 "요청 ID" 앞 8자를 보인다.
4. Error Boundary 3층: 루트(`src/app/global-error.tsx`, 루트 레이아웃까지 깨질 때), 화면(`src/app/(private)/error.tsx`, 헤더와 메뉴는 남기고 본문만), 모달(모달 틀 안. 모달만 오류로 바뀌고 닫을 수 있다).
5. 오류 화면은 운영에서 stack 대신 `digest` 를 보인다. 개발에서만 stack.
6. web-vitals: `useReportWebVitals` 로 지표를 `/api/vitals` 에 보낸다(sendBeacon). 서버는 모양을 확인하고 로그 한 줄. 잘못된 본문 400, 너무 큰 본문 413.
7. 테스트, 빌드, e2e 통과.

## 결정 (AI 가 정함)

1. Sentry 는 이번에 붙이지 않는다. 계정과 DSN 이 필요하고(외부 서비스 가입은 사용자 몫), 붙일 자리(`global-error.tsx`, 경계의 `componentDidCatch`, `/api/vitals`)만 만든다.
2. web-vitals 는 Vercel 로그로 본다. Speed Insights 는 대시보드에서 켜야 해서(외부 설정) 같은 이유로 미룬다.
