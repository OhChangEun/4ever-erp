## 완료 기준

1. 8곳 각각에서 버튼을 누르면 `window.confirm` 이 불리지 않고 앱 모달(role=dialog)이 뜬다. 모달 이름(제목)은 질문 문장이다. 확인을 누르면 요청이 한 번 나가고 성공하면 모달이 닫힌다.
2. 취소 버튼과 Esc 는 요청 없이 모달을 닫는다.
3. 구매 요청 반려와 발주서 반려 모달에는 label 이 연결된 여러 줄 사유 칸이 있다. 비어 있거나 공백뿐이면 확인 버튼이 눌리지 않고, 사유 칸의 설명(`aria-describedby`)으로 이유가 글자로 보이고, 요청이 나가지 않는다.
4. 입력한 사유가 구매 요청 반려는 본문 `comment`, 발주서 반려는 본문 `reason` 에 실린다(앞뒤 공백은 뺀다).
5. 반려 요청이 실패하면 모달이 닫히지 않고 입력한 사유가 그대로 남고 오류 문구가 보인다. 확인 버튼을 다시 누를 수 있다.
6. 요청 중에는 확인과 취소 버튼이 잠긴다. 확인을 두 번 눌러도 요청은 한 번이다.
7. 휴가 반려 모달에는 사유 칸이 없고 요청은 본문 없이 나간다.
8. 영어 로케일에서 모달 제목, 버튼(Cancel, OK), 사유 라벨과 안내가 영어다.
9. 모달이 열리면 포커스가 사유 칸으로 간다. 사유 칸이 없으면 취소 버튼으로 간다(확인 버튼이 아니다).
10. 라우트 첫 로드 JS 가 기준선보다 5KB 넘게 늘지 않는다.

## 결정 질문 (게이트 1)

조정자가 정한 것(그대로 따름):

1. 8곳 전부 앱 모달 체계로 여는 공통 확인 모달 하나로 바꾼다.
2. 반려 2곳(구매 요청, 발주서)은 사유 칸(여러 줄, 필수)을 둔다. 실패 시 모달과 입력을 지키고 오류를 보인다. 요청 중 버튼 잠금.
3. 휴가 반려의 사유 칸은 게이트웨이가 본문을 받는지로 정한다. 위 근거 표대로 받지 않으므로 두지 않는다.
4. 새 문구는 ko 와 en 을 같이. 버튼 글자는 기존 공통 키를 쓴다.
5. 접근성: 제목이 질문 문장, 사유 칸 label 연결, 오류는 `aria-describedby` 또는 role=alert, Esc 와 취소로 닫힘, 포커스는 사유 칸 또는 취소 버튼.
6. 번들 +5KB 한도. 넘으면 dynamic import.

AI 가 정한 것(`ai/decisions.md` "카드 확인 창과 반려 사유 (AI 결정)" 행):

1. 기존 공통 컴포넌트로는 안 된다. `ConflictDialog` 는 409 문구와 "최신 데이터 불러오기" 버튼이 굳어 있고 부모 영역 위에 덮는 용도다. `ModalStatusBox` 는 로딩과 오류 상자라 확인, 취소가 없다. `@everp/ui` 의 `Modal` 은 Radix 틀이 아닌 옛 오버레이다. `DropdownInputModal` 은 팝오버 입력이다. 그래서 새로 하나 만든다.
2. 위치는 `src/app/components/common/modal/ConfirmModal.tsx`. 앱의 `ModalProps`(`addModal` 이 넣는 `onClose`)와 next-intl 에 묶여 있어 `@everp/ui` 가 아니다. 그래서 스토리 대상이 아니다.
3. 모달은 `onConfirm` 이 돌려준 Promise 가 끝날 때까지 열려 있다. 호출부는 도메인 훅의 `mutateAsync` 를 넘긴다. `mutate` 의 호출별 콜백은 훅을 가진 컴포넌트가 사라지면 불리지 않는다(TanStack `MutationObserver` 의 `hasListeners()` 조건). 급여 상세 모달은 성공하면 자기부터 닫히므로 콜백 방식이면 확인 모달이 잠긴 채 남을 수 있다. 중복 제출은 모달의 확인 버튼 잠금이 막고, 뒤의 행 버튼은 지금처럼 `isPending` 으로 잠긴다. 리뷰 뒤 추가: 공통 빌더가 진행 중인 `mutateAsync` 재호출을 거절하고, `ModalProvider` 가 같은 버튼에서 같은 모달을 또 여는 것을 무시한다(아래 리뷰 절).
4. 사유가 없는 6곳도 같은 동작이다. 요청이 끝날 때까지 모달이 열려 있고 성공하면 닫힌다. 실패하면 열린 채 다시 누를 수 있다. 동작을 둘로 나누지 않으려는 것이다.
5. 실패 문구는 지금 있는 토스트를 그대로 쓴다(탭의 훅 `onError`). 모달 안에 같은 문구를 또 두지 않는다. 토스트는 모달보다 위 층(z 1100)이고 `aria-live` 영역이라 Radix 가 가리지 않는다(`aria-hidden` 1.2.6 은 `[aria-live]` 를 남긴다). 요청 중에 Esc 로 모달을 닫아도 탭이 토스트를 띄우므로 실패가 숨지 않는다. 이 앱의 다른 폼 모달(부서 수정 등)도 같은 방식이다.
6. 사유가 비면 확인 버튼을 `disabled` 로 두고, 사유 칸 아래에 안내 글자를 비어 있는 동안 계속 보인다(`aria-describedby`). 공백뿐인 입력도 빈 것으로 본다. 보낼 때 앞뒤 공백을 뺀다. 서버에 사유를 남기려는 카드라 공백 사유를 막았다.
7. 버튼 글자. 확인은 기존 `ui.confirm`(확인, OK)을 쓴다. 취소는 공통 메시지에 없어(`purchase.common.cancel` 만 있음) `common.cancel`(취소, Cancel)을 더했다.
8. 사유 길이 제한은 두지 않는다. 두 DTO 에 길이 제약이 없다.

### 겹친 모달의 처음 포커스

1. 현상. 급여 상세 모달 위에 확인 모달이 겹쳐 뜨면(사유 칸 없음) 처음 포커스가 닫기(X) 버튼에 갔다. 모달이 하나일 때는 "취소" 였다.
2. 원인. `ConfirmModal` 이 React 의 `autoFocus` 로 포커스를 줬다. React 는 commit 때 focus 를 부르는데 그때는 아래 모달의 Radix 포커스 가두기가 아직 살아 있어 포커스를 되가져간다. 그 뒤 위 모달의 가두기가 mount 되며 포커스가 자기 안에 없으니 첫 tabbable(닫기 버튼)로 보낸다.
3. jsdom 재현. 됐다. 수정 전 `PayrollDetailModal.test.tsx` "급여 모달 위에 겹쳐 뜬 확인 창의 처음 포커스는…" 와 `ConfirmModal.test.tsx` "다른 모달 위에 겹쳐 떠도 처음 포커스는… 사유 칸이다" 가 실패했다. 처음 테스트가 못 잡은 이유는 모달 하나만 띄워서다.
4. 처리. 모달 틀 `ModalContainer.tsx:60` 의 `Dialog.Content` 에 `onOpenAutoFocus` 를 걸었다. 안에 `[data-autofocus]` 요소가 있으면 Radix 기본 동작을 막고 그 요소에 focus 한다. 없으면 Radix 기본(첫 tabbable) 그대로다. 이 콜백은 위 모달의 가두기가 mount 된 뒤(아래 가두기가 멈춘 뒤) 불린다. `ConfirmModal` 의 사유 칸과 취소 버튼은 `autoFocus` 를 빼고 `data-autofocus` 표시로 바꿨다. `@everp/ui` 의 `Button` 은 남는 props 를 `<button>` 에 그대로 넘겨 고칠 것이 없었다.
5. 다른 모달 영향. `grep -rn "autoFocus" src packages` 결과는 `ConfirmModal` 두 곳뿐이었다. `data-autofocus` 를 쓰는 다른 모달이 없어 나머지 모달은 예전과 같다. 테스트 `ModalProvider.test.tsx` "표시(data-autofocus)가 없는 모달은 예전처럼 첫 tabbable(닫기 버튼)에 포커스가 간다" 로 고정했다(수정 전에도 통과).
6. 테스트 4개 추가, 수정 전 3개 실패. `ModalProvider.test.tsx` 2개(표시 없음, 표시 있음), `ConfirmModal.test.tsx` 1개(겹친 모달, 사유 칸), `PayrollDetailModal.test.tsx` 1개(급여 상세 위 확인, 취소 버튼).
7. 표시한 요소가 `disabled` 면 focus 가 먹지 않아 포커스가 모달 밖에 남는다. 지금 표시를 쓰는 곳(사유 칸, 취소 버튼)은 열릴 때 늘 활성이다. 새로 쓸 때 주의.
