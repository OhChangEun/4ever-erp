# 프로필 조회 경로 계약 불일치

- 출처: 구매 요청 부서 고정 결과 7
- 우선순위: 1(화면과 서버 일치)
- 브랜치: fix/profpath
- 구현: Claude(erp-dev)
- 상태: 완료(엔드포인트 삭제). 구현 에이전트는 ID 출처가 없어 멈췄고, 메인 세션이 삭제로 결정해 고쳤다.

## 결과

1. 백엔드 경로는 `GET /business/hrm/employees/by-internel-user/{internelUserId}` 다(`_4EVER_BE_GW/.../business/controller/HrmController.java:38` 의 `@RequestMapping("/business/hrm")`, `:147` 의 `@GetMapping`). 프런트 `USER_PROFILE_INFO`(`src/app/types/api.ts:131`)는 뒤 `/{internelUserId}` 가 빠졌다. 카드 설명대로다.
2. `internelUserId` 는 백엔드 access token 의 `user_id` claim 이다(`EverJwtAuthenticationConverter.java:28`, `ProfileController` 의 `user.getUserId()`).
3. 클라이언트에는 이 값이 없다.
   - `UserInfo.id`(`src/lib/auth/userInfo.ts`)는 숫자다. `/api/auth/me` 가 세션 `sub` 를 FNV-1a 로 해시한 값이라 되돌릴 수 없다(`src/app/api/auth/me/route.ts:6`).
   - 서버 세션(`src/lib/auth/session.ts`, `src/server/auth/session/store.ts`)도 `sub` 와 역할만 들고 `user_id` claim 은 꺼내 두지 않는다.
   - IdP 의 `sub` 가 `user_id` 와 같은 값인지는 인증 서버가 읽기 전용 사본(GW, ALARM 만 있음)에 없어 확인할 수 없다.
     카드 지시대로 추측하지 않고 멈췄다.
4. 이 경로를 부르는 코드가 없다. `USER_PROFILE_INFO` 를 쓰는 곳은 MSW 핸들러(`src/mocks/handlers/auth.handlers.ts:74`)뿐이고, git 이력에도 호출한 적이 없다(정의와 MSW 핸들러만. `7ecfb59` 에서 핸들러를 넣고 `6971a31` 에서 옮겼다). 프로필 화면은 `PROFILE_ENDPOINTS.PROFILE_INFO`(`/business/profile`)를 쓰고, 이 경로는 서버가 principal 에서 ID 를 꺼내므로 ID 가 필요 없다. 지금 화면이 실서버에 틀린 요청을 보내는 곳은 없다.
5. OpenAPI(`openapi/everp.yaml`)에는 이 경로가 아예 없다. 계약 테스트가 잡을 요청도 없다.
6. 테스트와 구현은 하지 않았다. 부를 곳이 없어 "요청 경로에 ID 가 들어간다"는 빨간 테스트를 걸 대상이 없고, ID 출처가 정해지지 않으면 엔드포인트 함수의 인자도 정할 수 없다.

## 결정 질문 (게이트 1)

1. 이 엔드포인트를 어떻게 할까.
   a. 지운다: `USER_PROFILE_INFO`, MSW 핸들러, `HRM_SELF_SERVICE` 의 항목을 뺀다. 테스트의 옛 목록(`OLD_SELF_SERVICE`)은 예전 표 스냅샷이라 둔다.
   b. 함수형으로 고치고 남긴다: 부를 곳이 생길 때 쓴다. ID 출처(아래 2)가 먼저 정해져야 한다.
   추천 a. 부르는 곳이 없고, 본인 프로필은 `/business/profile` 이 principal 로 해결한다.
2. b 를 고르면 `internelUserId` 를 어디서 얻나. 세션 생성 때 access token 의 `user_id` claim 을 꺼내 `/api/auth/me` 로 내려주는 방법이 있다. 인증 서버 확인이 필요하다.
3. 인가: `HRM_SELF_SERVICE`(`src/lib/authz/policy.ts:103`)는 정확히 같은 경로만 본다. 경로에 ID 가 붙으면 이 항목은 아무것도 허용하지 않게 되고, 요청은 HRM 역할 규칙으로 떨어진다. 접두사로 넓히면 로그인한 누구나 남의 ID 로 직원 정보(PII)를 읽을 수 있다. 백엔드 `HrmController.getEmployeeWithTrainingByInternelUserId` 는 경로 ID 와 principal 을 비교하지 않는다. 넓히지 않는 것을 추천한다.

## 별도 보고

1. `HRM_SELF_SERVICE` 의 `business/hrm/employees/by-internel-user` 는 백엔드에 없는 경로(ID 없음)를 허용 목록에 둔 것이다. 지금은 해가 없지만 위 결정 3 과 같이 정리해야 한다.
2. 백엔드 `HrmController` 의 `by-internel-user/{id}`, `/{id}/available-trainings`, `/{id}/attendance-records` 는 principal 확인 없이 아무 ID 나 받는다. 프런트 프록시의 HRM 역할 규칙이 유일한 막이다. 백엔드 쪽 문제라 손대지 않는다.

## 결정과 결과(메인 세션)

1. 엔드포인트를 지운다(AI 결정). 부르는 화면이 없고, 넣을 `internelUserId`(토큰의 `user_id`)가 클라이언트에 없다. 코드로 확인되는 사실이라 사람 결정이 필요 없다.
2. `USER_ENDPOINTS.USER_PROFILE_INFO`, 그 MSW 핸들러, 권한 표 `HRM_SELF_SERVICE` 의 `business/hrm/employees/by-internel-user` 를 지웠다. 허용 목록은 지금은 정확히 같은 경로만 통과시켜 구멍이 아니지만, 접두사 검사로 넓히는 순간 누구나 남의 직원 정보를 읽게 된다(백엔드가 ID 가 본인인지 보지 않는다).
3. 테스트(`policy.test.ts`, 의도한 변화): 인사 권한 없는 역할은 ID 가 있든 없든 이 경로를 못 부른다. 고치기 전에 실패한 단언은 ID 없는 경로의 SD_USER 하나다(`/u-2` 는 원래도 막혔다). 남은 허용 항목이 접두사로 넓혀지지 않는지도 함께 본다(휴가 승인, 반려 경로).
4. 남긴 것: 백엔드 `by-internel-user/{id}` 계열이 본인 확인을 안 하는 것은 백엔드 결함이라 이 저장소에서 못 고친다(팀 백엔드 담당에게 알릴 일).
5. 실험 메모: Codex 가 구매 카드에서 찾은 "경로 누락"은 사실이지만 부르는 곳이 없어 실제 영향은 없었다.
6. 확인: tsc, lint 0, vitest 658, build 통과. 리뷰(작성자 가린 Claude 에이전트) P2 1, P3 8 반영.
