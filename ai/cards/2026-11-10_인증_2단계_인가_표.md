- 출처: 계획 8절 3번(authz/policy.ts), 블록 4 타입의 "Role 유니온"
- 우선순위: 1 권한(페이지와 API 규칙이 어긋나면 화면은 열리고 데이터는 403), 4 유지보수성
- 브랜치: refac/인증_2단계_인가_표

## 현상

1. 같은 권한 규칙이 네 군데 있다: 페이지(`src/proxy.ts` ACCESS_RULES), API(프록시 라우트 PROXY_ACCESS_RULES), 메뉴 2곳(헤더, 사이드바 NAV_ITEMS). 역할 상수도 `src/lib/role.ts`, `src/app/types/role.constant.ts` 두 벌이다. 하나를 고치면 나머지를 손으로 맞춰야 한다.
2. `/warehouse`, `/low-stock` 은 페이지 규칙이 없다. 공급사나 고객사도 화면에 들어가고, 안의 재고 API(`scm-pp/iv`)만 403 으로 막혀 오류가 뜬다.
3. 페이지 규칙이 `startsWith('/sales')` 라 `/salesreport` 같은 다른 경로도 같은 규칙에 걸린다.
4. 역할은 전부 `string` 이다. 오타가 컴파일에서 안 잡힌다.

## 완료 기준

1. `src/lib/authz/policy.ts` 한 곳: `ROLES`, `Role` 유니온, `isRole`, 영역 표(페이지 경로, API 접두사, 역할), `canAccessPage`, `canAccessApi`, `menuRoles`.
2. 페이지 프록시, API 프록시, 메뉴 2곳이 이 표를 읽는다. 옛 역할 상수 파일 2개를 정리한다.
3. 예전 두 표와 같은 판정(테스트로 역할 15개 × 경로 전부 대조). 바뀌는 것은 의도한 두 가지뿐: 창고와 안전재고 페이지 규칙 추가, 경로를 세그먼트 단위로 맞추기.
4. 세션의 role 은 `Role` 이다. 목록 밖 role 이 든 세션은 무효.
5. 테스트, 빌드, e2e 통과. 새 경고 없음.

## 결정 (AI 가 정함, 사용자 2026-11-10 "끝까지 진행")

1. 창고, 안전재고 페이지는 재고와 같은 역할만 연다. 권한 없는 역할은 다른 페이지처럼 `/unauthorized` 로 간다. 화면에 들어가 403 오류만 보는 것보다 낫다(우선순위 1, 2).
2. 대시보드 메뉴를 공급사에게 숨기는 지금 동작은 유지한다(페이지는 열림). 표에 `menuHiddenFor` 로 적는다.
3. 표는 `src/lib` 에 둔다. 메뉴(클라이언트)도 읽어야 해서 server-only 로 두지 않는다. 비밀 값이 없고, 강제는 서버(페이지 프록시, API 프록시)만 한다.
