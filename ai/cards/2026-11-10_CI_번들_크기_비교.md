# CI 번들 크기 비교: 라우트별 첫 로드 JS 를 기준선과 대조

- 출처: 계획 16-1 "CI 고도화(번들 크기 diff)". 성능 블록(첫 로드 JS 를 카드마다 손으로 쟀다)의 자동화
- 우선순위: 3(빠르게 느껴진다를 지키는 장치), 4
- 브랜치: chore/CI_번들_크기_비교
- 크기: 반나절

## 현상

1. 첫 로드 JS 를 카드마다 손으로 `scripts/measure-bundle.mjs` 로 재서 적었다. 재는 것을 잊으면 늘어난 것을 모른다.
2. 이번 블록에서도 실제로 두 번 놓칠 뻔했다. 도메인 공개 API 한 파일(창고 +21.7KB), web-vitals 를 루트에 바로 둔 것(+4.8KB).

## 완료 기준

1. 기준선 `perf/bundle-baseline.json` 을 커밋한다(라우트별 gzip 바이트).
2. `scripts/bundle-diff.mjs` 가 기준선과 지금 빌드를 비교해 마크다운 표(라우트, 기준, 지금, 차이)를 만든다. 한 라우트라도 5KB 넘게 늘면 종료 코드 1. 새 라우트와 없어진 라우트는 표에 표시만 한다.
3. CI 가 빌드 뒤 이 비교를 돌려 job summary 에 표를 쓴다. 예산을 넘으면 CI 가 실패한다.
4. 의도한 증가는 같은 PR 에서 `npm run bundle:baseline` 으로 기준선을 갱신한다(diff 에 남는다).
5. 비교 함수 테스트.

## 결정 (AI 가 정함)

1. 예산은 라우트당 +5KB(gzip). 이번 블록의 의도한 증가(Radix Select 대신 floating-ui 훅 +6KB, 경계 +2KB)를 기준으로, 의도한 것은 기준선 갱신으로 드러내게 하는 값.
2. PR 코멘트 대신 job summary. 토큰 권한(pull-requests: write)을 늘리지 않는다.
3. Lighthouse CI 는 이번에 넣지 않는다. 데모 데이터가 MSW 목이라 점수가 실제 성능을 말하지 않고, CI 시간이 늘어난다. 랩 측정은 `npm run perf`(4배 CPU 감속)로 대신한다.

## 결과

1. `perf/bundle-baseline.json`(15개 라우트), `scripts/bundle-diff.mjs`, `npm run bundle:check`, `npm run bundle:baseline`. 비교 테스트 4개.
2. CI 는 빌드 뒤 `Bundle size` 단계에서 표를 job summary 에 쓰고, +5KB 넘게 는 라우트가 있으면 실패한다. 기준선을 6KB 줄인 가짜 파일로 실패 경로(종료 코드 1, "예산 초과")를 확인했다.
3. 리뷰 P1: 파이프 뒤 `tee` 가 실패를 가리던 것을 `shell: bash` 로 고쳤다.
4. 확인: lint 0 errors, tsc, vitest 347, build.
5. 남은 것: Lighthouse CI(결정 3), Dependabot 월 1회 묶음.
