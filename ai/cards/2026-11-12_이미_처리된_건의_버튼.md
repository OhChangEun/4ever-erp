- 화면: 재무 전표 목록, 영업 견적 목록과 검토 모달, 인사 교육 지정 모달과 급여 상세 모달(과 연 쪽 `PayrollManagement.tsx`), 생산 MRP 순소요, 생산 견적, 계획 주문 탭.
- 규칙 함수: `finance.service.ts` 의 `canProcessInvoice`, `sales.service.ts` 의 `canProcessQuote`. 목록과 모달이 같은 규칙을 쓴다(R22).
- 쿼리 키: 새로 쓰거나 바꾸지 않는다. 교육 지정 모달이 이미 있는 `trainingKeys.detail(employeeId)` 를 읽는다(교육 지정 mutation 이 이미 무효화하는 키).
- 목: `sales.handlers.ts` 견적 상세 한 줄(결정 4).
- 바꾸지 않는 것: 각 목록의 바깥 카드 래퍼(다른 카드), 공통 컴포넌트, 계약.

## 완료 기준

1. 재무 전표: 처리할 수 있는 전표만 체크박스가 열린다. 처리 요청이 성공하면 그 전표의 체크박스는 잠기고 체크가 풀리며 버튼이 잠긴다. 다시 눌러도 두 번째 POST 가 나가지 않는다. 완납 전표의 상세를 열어도 버튼이 열리지 않는다. 모르는 상태 값의 체크박스는 잠긴다.
2. 영업 견적 목록: `PENDING` 견적만 체크박스가 열린다. 고른 견적이 다시 받은 목록에서 `PENDING` 이 아니면 선택에서 빠지고 "검토 요청"이 잠긴다.
3. 견적 검토 모달: 상세 쿼리의 상태가 `PENDING` 일 때만 "즉시 납품"과 "생산에서 검토"가 보인다. 즉시 납품이 성공하면 같은 모달에서 버튼이 사라지고 두 번째 POST 가 나가지 않는다.
4. 교육 지정: 그 직원 이력에 있는 프로그램은 드롭다운에 없다. 지정 뒤 다시 열면 그 프로그램을 고를 수 없고 POST 가 나가지 않는다. 이력을 못 받으면 고를 수 없고 실패 문구를 보인다.
5. 급여 상세: 버튼은 상세 쿼리의 상태를 본다. 목록이 미지급이어도 상세가 지급완료면 버튼이 없다.
6. MRP 순소요: 전체 선택은 미전환 행만 넣는다. 전환 요청 본문에 전환된 품목이 없다.
7. 생산 견적: 확정 요청은 지금 목록에서 `UNCHECKED` 인 선택만 보낸다. 확정한 견적은 다음 확정에 가지 않는다.
8. 계획 주문: 고른 뒤 다시 받은 목록에서 상태가 바뀐 주문은 선택에서 빠진다.
9. e2e: 새로 로그인해 전표 처리 요청 뒤 다시 요청할 수 없고, 견적 즉시 납품 뒤 그 견적을 다시 고를 수 없다. 같은 서버에서 두 번 돌려도 통과한다.

## 결정 (AI 결정, `ai/decisions.md` "카드 이미 처리된 건의 버튼 (AI 결정)" 행)

1. 전표의 처리 가능 상태는 화면이 예전부터 열어 두던 아는 값만 남긴다. 매출(ar)과 공급사(supplierAp)는 `PENDING`, `RESPONSE_PENDING`, 사내 매입(ap)은 `UNPAID`, `RESPONSE_PENDING`. 예전 잠금 목록은 그대로 잠그고, 모르는 값은 새로 잠근다. 사내 매입 `RESPONSE_PENDING` 은 처음에 잠갔다가 리뷰 뒤 조정자 결정으로 다시 열었다. 공급사가 매입 전표를 이 값으로 바꾸는 API 가 있고(`FcmController.java:247-250`) 예전 화면도 열어 두었다. 응답 대기 뒤 사내가 처리하는 흐름으로 본다(verified=false). 게이트웨이 완료 설명이 "미납/확인요청 상태"라 매출 `UNPAID` 도 될 수 있지만 지금 화면이 잠그는 값이라 열지 않았다(별도 보고 3).
2. 견적의 처리 가능 상태는 `PENDING` 하나. `REVIEW` 는 검토 요청을 이미 보내 생산이 검토하는 중이라 영업 화면이 할 일이 아니다(리뷰 뒤 조정자 확인, 잠금 유지). 즉시 납품을 허용할지도 근거가 없다. 모르는 쪽은 숨긴다(우선순위 1).
3. 숨김이냐 잠금이냐는 그 화면이 이미 쓰던 방식. 목록의 체크박스와 처리 버튼은 잠금(전표, 생산 탭과 같다), 견적 검토 모달의 다음 단계 칸은 숨김(그 칸이 원래 재고 확인 뒤에만 보이는 조건부 칸이다), 급여 버튼은 숨김(예전 그대로), 교육 지정은 드롭다운에서 뺀다(공통 `Dropdown` 에 항목 잠금이 없다).
4. 견적 상세 목 한 줄. 상세 목은 어떤 id 로 물어도 `APPROVAL` 을 줘서, 모달이 상세 값을 보게 하면 목록에서 `PENDING` 인 견적도 데모에서 버튼이 안 뜬다. 브리프는 목 수정을 "별도 보고"로 하라고 했지만 그러면 데모의 즉시 납품이 막히고 e2e(할 일 4)를 쓸 수 없다. 상세가 목록의 그 견적 상태를 따르게 한 줄만 고쳤다(목록에 없는 id 는 예전처럼 저장된 상태, 없으면 `APPROVAL`).
5. 기존 테스트 고정값 한 곳. `sales.remaining-defects.test.tsx` 의 즉시 납품 두 테스트(언어 둘이라 4개)는 기본 목 상세(`APPROVAL`, 승인된 견적)에서 즉시 납품을 누른다. 이 카드가 막는 동작 그 자체다. 단언은 그대로 두고, 상세를 `PENDING` 으로 주는 `server.use` 한 줄을 그 테스트의 준비 함수에 넣었다.
6. 선택은 state 에 id 만 두고, 그릴 때 지금 목록에서 처리할 수 있는 행으로 거른다(R01, R02). 다른 페이지에서는 선택이 없는 것으로 보고 버튼이 잠긴다(돌아오면 다시 체크돼 보인다). 예전엔 전표와 견적에서 안 보이는 페이지의 선택으로 처리 요청을 보낼 수 있었다.
7. 생산 견적 탭의 "미확인 견적을 고르라"는 경고(`production.quotation.selectUnchecked`)는 선택을 거르면서 닿을 수 없는 분기가 돼 코드와 ko, en 메시지에서 뺐다.
8. 교육 지정 모달은 이력 조회가 끝나기 전에는 드롭다운을 잠근다. 이력에 있으면 완료든 미완료든 뺀다(재교육 정책을 모른다).

## 별도 보고

1. 출하 상세 모달의 "배송 시작"은 상세 쿼리의 상태를 보지 않는다. 처리 뒤 상세 값이 무엇인지 근거가 없고(`Object`), 목 상세도 쓰기를 따르지 않는다. 지금은 성공하면 모달이 닫히고 목록에서 행이 빠져 흔한 경로는 막혀 있다.
2. 안전재고 "선택 품목 발주"는 이미 구매 요청한 품목을 화면이 알 수 없다. 목록 응답에 그런 필드가 없다. 서버 계약 질문이다.
3. 매출 전표 완료 API 설명은 "미납/확인요청 상태"(`FcmController.java:178`)인데 화면은 예전부터 매출 `UNPAID` 를 잠근다. 서버가 생기면 확인한다.
4. 교육 프로그램 드롭다운 목은 `prog-001` 하나이고 모든 직원 이력에 `prog-001` 이 이미 있다. 그래서 데모에서는 교육 지정 모달에 고를 것이 없다. 프로그램 추가 목이 만든 프로그램도 드롭다운에 안 나온다. 목 수정은 하지 않았다.
5. 견적 상세 목은 목록에 없는 id 에 여전히 고정 본문(`QT-2026-001`, `APPROVAL`)을 준다(지난 카드 별도 보고 8).
6. 사내 매입 `RESPONSE_PENDING` 을 다시 열었다(결정 1). 이 상태에서 사내 "처리 요청"이 실제로 필요한지, 이미 요청한 뒤라 막아야 하는지는 응답이 `Object` 라 사본으로 알 수 없다. 서버가 생기면 확인한다. 견적 `REVIEW` 견적을 생산 확인 뒤 영업이 납품하는 흐름이 있는지도 같은 질문이다(지금은 영업 화면에 다음 단계 버튼이 없다).
