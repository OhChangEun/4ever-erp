# OpenAPI 계약 1: 창고 도메인으로 파이프라인 세우기

- 출처: 계획 16-1 "OpenAPI 계약 우선 + 생성", 결정 기록 "목 레이어 두 벌" 행. 플랫폼 블록 두 번째 카드(첫 카드는 목 한 벌)
- 우선순위: 1(화면 타입, 목, 서버 응답 모양이 따로 놀면 화면이 서버와 어긋난다), 4
- 브랜치: feat/OpenAPI_계약_1_창고
- 크기: 1일

## 현상

1. API 모양을 적은 곳이 세 군데다. 손으로 쓴 타입(`src/app/(private)/warehouse/types/*`), MSW 핸들러의 목 데이터, 일부 도메인의 zod 스키마. 셋을 묶는 원본이 없다.
2. MSW 핸들러는 타입 없이 객체를 돌려준다. 필드 이름이 틀려도 컴파일이 통과한다.
3. 서버가 생기면 무엇을 맞춰야 하는지 적힌 문서가 없다.

## 영향 범위

창고 도메인(`WAREHOUSE_ENDPOINTS` 6개 요청), 창고 MSW 핸들러, 창고 타입 파일. 쿼리 키와 화면 동작은 그대로.

## 완료 기준

1. `openapi/everp.yaml`(OpenAPI 3.1)이 계약 원본이다. 공통 래퍼(`ApiResponse`, `Page`, 기간 통계)와 창고 요청 6개.
2. 화면이 부르는 창고 요청(메서드와 경로) 6개가 전부 계약에 있다(테스트).
3. 창고 GET 응답(MSW)이 계약의 응답 스키마를 만족한다. 계약을 zod(`z.fromJSONSchema`)로 바꿔 런타임에 확인한다(테스트).
4. 생성 타입 `src/lib/api/openapi.gen.ts` 는 계약에서 `openapi-typescript` 로 만든다. 커밋된 파일이 계약과 다르면 테스트가 실패한다(CI 의 drift 검사).
5. 창고 MSW 핸들러는 `openapi-msw` 로 쓴다. 계약에 없는 경로나 틀린 응답 모양은 `tsc` 가 막는다.
6. 창고 타입 파일은 생성 타입의 별칭이 된다. 손으로 쓴 응답 필드 목록은 0.
7. 테스트, 빌드, e2e 통과.

## 남길 수치

창고 손 타입 줄 수(전후), 계약 경로 수, 생성 타입 줄 수.

## 결정 (AI 가 정함)

1. 계약 원본은 YAML 한 파일(`openapi/everp.yaml`). 도메인이 늘면 `paths` 만 늘린다. 파일 분할은 300줄을 넘으면.
2. 생성은 `openapi-typescript` 7(타입만), 목은 `openapi-msw` 2(타입 붙은 MSW). orval 처럼 fetcher 까지 만드는 도구는 안 쓴다. axios 인스턴스(AppError 인터셉터)를 그대로 쓰려고.
3. drift 검사는 vitest 안에서 생성기를 직접 돌려 비교한다. CI 단계를 따로 늘리지 않는다.

## 결과

1. 계약 `openapi/everp.yaml` 279줄. 공통 스키마 4개(ApiEnvelope, ApiError, Page, Stat)와 창고 경로 4개(요청 6개).
2. 생성 타입 `src/lib/api/openapi.gen.ts` 338줄(`npm run openapi`). eslint 와 prettier 대상에서 뺐다.
3. 창고 타입 파일 5개는 76줄 → 36줄. 응답과 요청 필드를 손으로 적은 줄은 0. 모달 props 같은 화면 타입만 남았다.
4. 창고 MSW 핸들러는 `src/mocks/handlers/warehouse.handlers.ts` 로 옮기고 `openapi-msw` 로 썼다. 필드 이름을 틀리면 tsc 가 막는 것을 확인했다.
5. 계약 테스트 3개: 화면 요청 6개가 계약에 있다, GET 응답 4개가 계약 스키마를 만족한다, 생성 타입이 계약과 같다. 목 데이터를 일부러 틀리면 실패하는 것을 확인했다.
6. 새 타입 덕에 창고 목록의 항상 거짓인 조건(`!warehouses`)을 린트가 잡아 지웠다.
7. 첫 로드 JS 변화 없음(타입만). 확인: lint 0 errors(경고 474), tsc, vitest 308, build, e2e 57 통과 2 skip.
8. 다음: 나머지 도메인을 계약으로 옮긴다. 영업, 구매, 생산의 손 zod 스키마는 계약에서 꺼내게 바꾼다.
