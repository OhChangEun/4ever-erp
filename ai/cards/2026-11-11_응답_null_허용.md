# 응답 null 허용

- 출처: 서버 계약 점검
- 우선순위: 1(값이 틀리면 형식 오류), 2(필드 하나 때문에 화면 전체를 막지 않는다)
- 브랜치: fix/zodnull
- 구현: Claude(erp-dev)

## 현상

zod 를 붙일 때(`f769122b` 영업, 구매, 생산 / `9131a15b` 나머지) 응답 필드 몇 개가 non-null `z.string()` 이 됐다. 그 전 화면은 같은 필드에 null 가드(`?? '-'`, `|| '-'`, `?.`)를 두고 있었고, 실서버가 null 을 안 준다는 근거는 없다. 서버가 그중 하나라도 null 로 보내면 화면 전체가 "형식 오류"가 된다.

## 완료 기준

1. 가드가 있던 글자 필드 각각을 null 로 바꾸거나 키를 빼도 읽기가 성공한다(`src/test/contract/nullableFields.contract.test.ts`, 23개씩 46개).
2. 같은 읽기에서 ID 가 빠지면 여전히 형식 오류다(같은 파일, 10개).
3. 도메인마다 화면 하나가 null 이나 키 없는 필드를 `-` 로 그리고 나머지를 그린다(생산, 영업, 인사, 재고, 창고 각 `*.nullable.test.tsx`).
4. 계약(`openapi/everp.yaml`)과 생성 타입(`pnpm openapi`)이 같고 두 목이 계속 통과한다.

## 찾는 방법

가드 기준: 필드 자체에 `?? x`, `|| x`, `?.`, `&&` 가 붙은 곳. `parent?.field` 처럼 로딩 중인 부모를 막던 것, 폼 입력 검증(`!form.x ||`), 생성 모드 초기값(`initialData?.x || ''`)은 제외. 영업, 구매, 생산은 `f769122b^`, 나머지는 `9131a15b^` 의 화면 코드를 스키마 필드 이름으로 훑었다(린트 3차 `4d57ca91` 에서 지운 가드 포함).

남긴 것(엄격): ID, 상태 코드, 금액과 수량(MPS 수요 등 숫자 4개, 단가), 목록 구조(content, page, 항목 배열, 기간 키), 출퇴근 행의 직원 객체(행의 주인이라 ID 와 같게 봄).

## 결정 (AI 가 정함)

1. 위 기준의 글자 필드 23개만 null 과 키 누락 허용(리뷰 뒤 nullish). `ai/decisions.md` 같은 날 행.
2. 출퇴근 목록 직원은 급여 상세와 같은 zod 조각을 쓰고 있었다. 급여 상세 직원은 가드가 없었으므로 출퇴근 쪽만 이름과 직급을 푼 객체로 나눴다. 계약의 `EmployeeInfo` 는 출퇴근만 쓴다.
3. MES 공정 담당자는 객체째 null 허용(예전 `operation.manager?.name`). 시작 전 공정은 담당자가 없을 수 있다.

## 결과

1. 빈 값 허용 필드(계약은 required 에서 빼고 nullable, 생성 타입은 `?: string | null`, zod 는 `z.nullish`):
   1. 생산 MES 상세 `operations[].startedAt`, `finishedAt`, `manager`, `manager.name`
   2. 생산 MRP 순소요 목록 `content[].procurementStartDate`, `expectedArrivalDate`
   3. 생산 견적 목록 `content[].dueDate`
   4. 영업 주문 상세 `note`
   5. 인사 부서 목록 `content[].description`, `managerName`, `location`, `establishedDate`
   6. 인사 출퇴근 목록 `content[].employee.employeeName`, `position`
   7. 인사 교육 현황 `items[].lastTrainingDate`
   8. 재고 목록 `content[].warehouseName`
   9. 재고 상세 `lastModified`
   10. 창고 상세 `warehouseInfo.warehouseName`, `location`, `description`, `manager.managerName`, `managerPhoneNumber`, `managerEmail`
2. 화면: 빈 값(null 이나 키 없음)은 `-`(창고 상세 6칸, 재고 상세 수정일, 교육 현황 최근 교육일, 부서 카드 부서장, 재고 목록 창고명, MES 담당자). 창고 관리 폼은 예전처럼 `''` 로 채운다. 부서 수정과 출퇴근 수정 폼은 예전엔 가드 없이 값을 그대로 넣었고, 이제 비면 `''` 로 채운다. 그래서 설명이 없는 부서를 저장하면 설명이 `''` 로 간다(수정 본문 계약은 필수 string 이라 `''` 도 맞다). 3D 창고 이름이 없으면 기존 "미지정 창고" 문구, 묶음 키는 `no-name`.
3. 카드 예시 중 재고 상세 `description`, `stockMovement[].note`, `referenceNumber`, 발주 상세 `note` 는 zod 전에도 가드가 없었다(재고 이동 메모 가드는 주석 처리 상태). 기준대로 그대로 엄격하다.
4. 테스트: 새 테스트 28개가 구현 전 빨간불(형식 오류), 구현 뒤 초록. ID 10개는 구현 전에도 초록이다(엄격함을 지키는 테스트라 의도한 것). 목 응답을 고쳐 내보내는 도우미를 `src/test/contract/mockData.ts` 로 빼고 기존 `guardedReads` 계약 테스트도 이것을 쓴다.
5. 기존 `guardedReads` 계약 테스트의 확인 필드 4개를 바꿨다(이 카드가 null 을 받기로 한 필드라서). 교육 현황 `lastTrainingDate` → `employeeId`, 재고 상세 `lastModified` → `itemId`, 재고 목록 `warehouseName` → `itemId`, 창고 상세 `description` → `warehouseInfo.statusCode`. 테스트 개수와 강도는 같다.
6. 확인: `tsc --noEmit` 통과, `eslint .` 0/0, `vitest run` 117 파일 854 통과(리뷰 반영 뒤), `pnpm build` 통과.

## 남은 것

1. 실서버 응답으로 23개 필드가 실제로 null 로 오는지 확인(verified=false). 안 온다는 게 확인되면 다시 엄격하게 돌려도 된다.
2. MPS 수요, 필요 재고, 생산 필요량, 계획 생산량은 예전에 `?? '-'` 가드가 있었지만 수량이라 엄격하게 뒀다. 주가 비면 서버가 null 을 줄 수 있는지 사람이 정해야 한다.
3. 사람 diff 검토 전이다.

## 리뷰 반영

작성자를 가린 Claude 리뷰어. P0, P1 없음.

1. P2 nullish: 23개 필드를 `z.nullable` 에서 `z.nullish` 로 바꿨다. 예전 가드(`?.`, `??`, `||`)가 undefined 도 막았기 때문이다. 계약에서는 required 에서 빼고 nullable 로 둬서 생성 타입이 `?: string | null` 이다. 3D 창고 이름은 없으면 null 로 맞췄다. 계약 테스트와 화면 테스트 5개에 키 누락 경우를 더했다.
2. P3 부서 수정 폼: 결과 2의 "예전처럼" 문장을 사실대로 고쳤다. 설명이 없으면 `''` 로 저장된다는 것도 결정 행에 적었다.
3. P3 결정 행 이유: 출퇴근 직원 객체는 엄격, MES 담당자는 풀었다, 배열은 목록 구조라 엄격. 이 셋을 적었다.
4. P3 테스트: 재고 수정일 칸 값이 정확히 `-` 인지 비교한다. MES 에서 담당자는 있고 이름만 null 인 경우도 더했다.
5. `ai/decisions.md` 를 prettier 로 다시 정렬했다(이 행에 물결표 없음).
