## 현상

데모 목은 목록에 없는 id 로 상세를 부르면 기본 행 본문에 그 id 를 실어 200 으로 준다. 예: `GET /business/sd/quotations/nope-1` 이 한빛전자 견적(qt-001 본문)을 `quotationId: nope-1` 로 준다(`src/mocks/handlers/sales.handlers.ts:366`). 앞 카드가 "계약에 404 가 없다"(`grep 404 openapi/everp.yaml` 0건)를 이유로 이렇게 정했다. 지워진 건, 다른 로그인이 만든 건, 목이 50건 상한으로 밀어낸 건이 다 정상 상세로 보인다.

## 근거: 게이트웨이가 없는 건에 주는 것

게이트웨이 사본 `~/dev/_team-be-readonly/_4EVER_BE_GW`(커밋 7dd1211). 실제로 도는 코드만 적는다. `*_NOT_FOUND` 오류 코드를 던지는 곳은 주석 처리된 옛 목(`mockdata/scmpp/controller/MmController.java:396` 등)뿐이라 근거로 쓰지 않는다.

1. 실패 본문 모양. `common/response/ApiResponse.java:15` 가 `@JsonInclude(NON_NULL)`, `:41-49` 의 `fail(message, status, errors)` 는 `success: false`, `data: null`. null 은 빠지므로 본문은 `{ status, success: false, message }` 이고 `errors` 가 있을 때만 붙는다. `data` 키는 없다.
2. 상세 19개 중 9개(영업 견적, 주문, 고객, 매입과 매출 전표, 인사 직급, 급여, 교육 현황, 교육 프로그램)는 서비스가 업스트림 4xx 를 잡아 그 상태 코드로 `ApiResponse.fail(작업 + " 중 오류가 발생했습니다.", 상태, null)` 을 준다. 견적: `business/service/impl/SdHttpServiceImpl.java:351-374`(`:367` 에서 `handleWebClientError("견적 상세 조회", ex)`), `:704-715`. 같은 함수가 `HrmHttpServiceImpl.java:1637-1645`, `FcmHttpServiceImpl.java:611-619`. 오류 코드 필드는 없다(`errors` 가 null).
3. 나머지 10개(BOM, MES, 제품, 공급사, 구매 요청, 발주, 재고 품목, 창고, 출고 준비, 생산중 주문)는 컨트롤러가 업스트림 상태와 본문 문자열을 그대로 넘긴다. MES: `scm/pp/controller/PpController.java:188-208`(`exchangeToMono` 로 `response.statusCode()` 와 본문). 같은 모양이 `PpController.java:85, 827`, `scm/mm/controller/MmController.java:83, 270, 463`, `scm/im/controller/ImController.java:139, 369`, `scm/im/controller/OrderController.java:159, 185`. 이 10개의 404 본문은 업스트림이 정하고, 업스트림 코드는 사본에 없다.
4. 업스트림이 없는 id 에 실제로 404 를 주는지는 사본에 없다(verified=false). `ErrorCode.java:24-100` 의 `QUOTATION_NOT_FOUND(1022, 404)` 같은 404 코드는 게이트웨이 전역 처리기(`common/exception/handler/GlobalExceptionHandler.java:36-71`)가 `errors: { code }` 로 내보내는 길이 있지만, 게이트웨이 자신이 던지는 곳은 위 옛 목뿐이다.

## 별도 보고

1. 404 전용 문구. 상세 모달 19곳이 404 를 받아도 "불러오지 못했다" 류 일반 문구만 보인다(견적 "견적서를 불러오는 중 오류가 발생했습니다.", MES "데이터를 불러오는 데 실패했습니다."). 이미 있는 `errors.notFound`("요청한 데이터를 찾을 수 없습니다.")를 404 일 때 쓰면 "사라진 건" 이 드러난다. 메시지 파일을 같이 고치는 카드가 끝난 뒤 19곳을 한 번에 하는 카드 후보.
2. 카드 후보 "상세 모달 오류면 닫기 = 모달 닫기로 일괄". 상세 모달의 조회 오류 창 닫기가 오류 창만 닫고(`useDismissibleError`) 빈 틀이 남는다. 견적 상세는 번호와 고객이 빈칸, 합계 ₩0 이 실제 값처럼 보인다(`QuoteDetailModal.tsx:31-35`, 우선순위 2). 이 카드 전부터 500, 네트워크 오류에 같았고 404 로 "다른 사용자가 지운 건" 에서도 나오게 됐다. 같은 훅으로 상세를 받는 모달 11곳: 영업 `QuoteDetailModal`, `QuoteReviewModal`, `SalesOrderDetailModal`, `CustomerDetailModal`, 재고 `InventoryDetailModal`, `ShippingDetailModal`, 구매 `PurchaseRequestDetailModal`, `PurchaseOrderDetailModal`, 재무 `InvoiceDetailModal`, 창고 `WarehouseDetailModal`, `ManageWarehouseModal`. MES 상세가 이번에 한 방식(`ModalStatusBox` 의 `onClose` 에 모달의 `onClose`)으로 바꾼다. 조정자 지시로 이 카드에서는 안 고친다.
