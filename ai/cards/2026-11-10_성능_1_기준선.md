# 성능 1: 기준선 측정

- 출처: 계획 9절 1번("숫자 없이 고치지 않는다")
- 우선순위: 3 빠르게 느껴진다(측정 도구만, 동작 변화 없음)
- 브랜치: chore/성능_1_기준선
- 크기: 반나절

## 현상

1. 성능을 잴 도구가 없다. Next 16(Turbopack) 빌드는 라우트별 First Load JS 를 출력하지 않는다.
2. 그래서 무엇이 무거운지, 고친 뒤 얼마나 줄었는지 말할 수 없다.

## 완료 기준

1. `scripts/measure-bundle.mjs`: 빌드 결과의 정적 HTML 이 처음 받는 청크를 모아 라우트별 크기(gzip)와 큰 패키지를 표로.
2. `perf/measure.spec.ts`(+ `playwright.perf.config.ts`): 운영 빌드에서 화면 3개의 LCP, 긴 작업 합, 스크립트 전송량, 첫 진입과 탭 전환 API 수. CPU 4배 느리게, 3번 중앙값. CI 밖.
3. `npm run perf` 하나로 둘 다. 결과를 ARCHITECTURE.md 8-1절에.

## 결정 (AI 가 정함)

1. Lighthouse 와 bundle-analyzer 는 들이지 않는다. 브라우저 성능 API 와 빌드 결과 파싱으로 같은 질문(무엇이 무거운가, 줄었나)에 답한다. 새 의존성 0.
2. 측정 도구만 더한 카드라 Codex 리뷰는 생략한다(Playwright 카드와 같은 기준).

## 결과

1. 기준선: 첫 로드 JS 는 재무, 영업, 재고 574KB(gzip)가 가장 크고 로그인 176KB. 큰 청크는 recharts 121.6, zod 83.9, MUI 날짜 선택기와 date-fns 70.9, framer-motion 70.5(KB).
2. 화면(CPU 4배): 재고 LCP 360ms, 긴 작업 130ms 로 가장 무겁다. 탭을 다시 열면 API 0(캐시).
3. 다음 카드: MUI 제거(결정 2), recharts dynamic import, zod/mini 검토, framer-motion 사용처 정리.
