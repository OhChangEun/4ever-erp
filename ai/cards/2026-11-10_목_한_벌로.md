# 목 한 벌로: 서버 목 라우트가 MSW 핸들러를 쓴다

- 출처: 계획 16-1 "OpenAPI 계약 우선 + 생성"과 결정 기록 "목 레이어 두 벌" 행. 플랫폼 블록 첫 카드
- 우선순위: 1(테스트가 보는 목과 화면이 보는 목이 달라 거짓 통과), 4
- 브랜치: refac/목_한_벌로
- 크기: 반나절

## 현상

1. 목이 두 벌이다. 서버 목 `src/app/api/[...slug]/route.ts`(1,902줄, if 문 160개)는 Vercel 데모와 e2e 가 보고, MSW `src/mocks/handlers/*`(2,592줄, 핸들러 161개)는 단위 테스트가 본다.
2. 같은 GET 경로 103개를 두 목에 보내 본문을 비교하면 8개가 다르다(2026-11-10 측정). 단위 테스트가 통과해도 데모 화면은 다를 수 있다.
3. MSW 쪽에 경로 가림 결함 3건. MSW 는 등록 순서로 맞추는데 `:param` 경로가 구체 경로보다 앞에 있다.
   1. `GET business/hrm/payroll/statuses` 가 급여 상세(`payroll/:payrollId`)로 간다. 급여 상태 드롭다운이 단위 테스트에서 상세 객체를 받는다.
   2. `GET scm-pp/iv/items/toggle` 이 품목 상세로 간다. 품목 드롭다운도 같다.
   3. `PATCH alarm/notifications/all/read` 가 개별 읽음으로 간다.

## 영향 범위

목 레이어만. 화면 코드, 쿼리 키, 인증 경로는 그대로. 서버 목에만 있던 경로 5개(login, logout, me, `fcm/statistics` 오타 별칭, `pp/status/toggle`)는 앱이 부르지 않는다(grep 확인).

## 완료 기준

1. 서버 목 라우트는 MSW `getResponse(handlers, request, { baseUrl })` 로 응답한다. 손으로 쓴 분기는 0.
2. 구체 GET 경로마다 서버 목과 MSW 의 본문이 같다(테스트).
3. 실패 시나리오(`x-mock-scenario`, `?mockScenario=`)가 서버 목에서도 먹는다.
4. 모르는 경로는 404 와 `{ success: false }`.
5. MSW 핸들러에서 구체 경로가 앞의 `:param` 경로에 가려지지 않는다(테스트가 전 핸들러를 검사).
6. 단위, 계약, e2e, 빌드 통과.
