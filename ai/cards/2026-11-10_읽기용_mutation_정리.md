# 읽기용 mutation 정리

- 출처: mutation 훅 통일 블록의 남은 4곳(`ARCHITECTURE.md` 5절)
- 우선순위: 2 실패 노출(MRP 모달 조회 실패 시 빈 표로 구매 요청 가능), 4 유지보수성
- 브랜치: refac/읽기용_mutation_정리
- 크기: 반나절

## 현상

컴포넌트 안에 남은 `useMutation` 4곳을 성격별로 나누면 다음과 같다.

1. MRP 자재 구매 요청 모달(`MrpPurchaseRequestModal.tsx:38`): 마운트할 때 `useEffect` 로 품목 정보를 조회(mutation)하고 결과를 `editableOrders` state 에 복사한다. 그 state 를 편집하는 곳이 없다(R01 파생 상태, R02 불필요한 effect). 조회가 실패하면 토스트만 띄우고 빈 표에서 "구매 요청 확정"이 눌린다. 빈 구매 요청이 서버로 간다(우선순위 2).
2. BOM 생성 모달의 자재 로드(`BomInputFormModal.tsx:155`): 같은 행이 `useQuery(bomKeys.materialInfo(itemId))` 로 이미 같은 자재를 가져온다. mutation 결과는 아무 데도 안 쓴다. 자재를 고를 때마다 같은 요청이 두 번 간다(R17).
3. 견적 시뮬레이션(`QuotationTab.tsx:77`): 끝나면 견적 목록을 무효화한다. 서버 상태를 바꾸는 쓰기라 mutation 이 맞다. 도메인 훅이 아니라 컴포넌트에 있고, 실패 문구에 오류 종류가 없다.
4. 견적 검토의 재고 확인(`QuoteReviewModal.tsx:58`): 버튼으로 한 번 계산하는 요청(POST). 결과를 캐시할 이유가 없어 mutation 이 맞다. 도메인 훅이 아니다.

## 완료 기준

1. MRP 모달: 품목 정보는 `useQuery` 로 조회하고 표는 조회 결과에서 계산한다(state 복사와 effect 없음). 조회 실패면 `ModalStatusBox` 오류를 보이고 "구매 요청 확정" 버튼이 없다. 로딩 중에도 없다.
2. BOM 모달: 중복 mutation 을 지운다. 자재 정보 조회가 실패하면 행에 "불러오지 못함"이 보인다.
3. 시뮬레이션과 재고 확인은 도메인 훅(`production.mutations.ts`, `sales.mutations.ts`)으로 옮긴다. 공통 빌더의 중복 제출 안전망을 받는다. 시뮬레이션은 견적 목록을 무효화한다.
4. 컴포넌트 안 `useMutation` 0건.
5. 기존 테스트, 린트, 빌드, e2e 통과.
