## 근거

- 주문 목록: 게이트웨이 `_4EVER_BE_GW/.../business/controller/SdController.java:336,338` 이 `@RequestParam(name = "startDate")`, `@RequestParam(name = "endDate")` 를 받는다. `SdHttpServiceImpl.java:256-257` 도 업스트림에 같은 이름으로 넘긴다. Spring 은 모르는 이름(`start`, `end`)을 무시하므로 날짜 필터가 조용히 빠진다.
- 견적 상태: `business/constants/QuotationStatus.java:13` 의 enum 은 `APPROVAL`, 목록 DTO 주석 `business/dto/quotation/QuotationListItemDto.java:20` 도 `APPROVAL`. 승인 API 설명 `SdController.java:392` 는 `APPROVED`. 상세는 `SdHttpServiceImpl.java:351` 이 업스트림 응답을 `Object` 로 프록시하고 `QuotationDetailDto.statusCode` 는 자유 문자열이라 사본으로는 실제 값을 확정할 수 없다.
- 단위: `business/dto/quotation/QuotationItemDto.java` 의 `uomName`, `business/dto/sd/response/OrderItemDto.java` 의 `uonName` 모두 자유 문자열. 코드 목록의 근거는 없고, 주석 처리된 목 `mockdata/scmpp/controller/ImController.java:44` 의 `UOM_NAMES`(EA, KG, M, L, SET)를 참고만 했다.

## 결과

1. 주문 날짜 필터가 `start`, `end` 로 나가서 게이트웨이가 무시했다. `OrderQueryParams` 를 `startDate`, `endDate` 로 바꾸고 `sales.api.ts`, `SalesOrderList.tsx` 를 맞췄다. 계약 `/business/sd/orders` GET 에 게이트웨이와 같은 쿼리 파라미터 7개를 선언하고 `openapi.gen.ts` 를 다시 만들었다. MSW 주문 목록은 `startDate`, `endDate` 로만 주문일을 거른다(모르는 이름은 서버처럼 무시). 옛 이름을 보내면 계약 테스트와 목 필터 테스트가 실패하는 것을 api 를 잠깐 되돌려 확인했다.
2. 견적 상세 zod enum 과 계약 `QuoteDetail.statusCode` enum 이 `APPROVAL` 을 몰라서 형식 오류로 막힐 수 있었다. 두 곳과 `QuoteStatus` 타입에 `APPROVAL` 만 더했다. 다른 모르는 값(`APPROVE`)은 계속 형식 오류다. 표시는 기존 `StatusLabel` 과 공통 `status.APPROVAL`(승인, Approved). MSW 견적 상세는 게이트웨이 enum 인 `APPROVAL` 을 보내고 목록은 `APPROVED` 그대로라 두 형식이 기본 계약 테스트를 다 지난다.
3. 견적 상세와 주문 상세가 단위 코드 `EA` 를 그대로 보였다. 앱에 단위 글자 관례가 없어(재고, 생산, 구매도 코드 그대로) 영업 메시지 `sales.common.uom` 을 새로 두고 `sales.labels.ts` 의 `useSalesLabels().uomLabel` 로 두 모달이 같이 쓴다(재고 `inventory.labels.ts` 와 같은 모양). EA 는 개, pcs. 모르는 코드는 숨기지 않고 코드 그대로 보인다. 서버로 보내는 값은 바뀌지 않는다(영업 화면에서 단위를 보내는 요청은 없다).

## 리뷰 반영

작성자를 가린 Claude 리뷰어의 P2 1개, P3 5개.

1. P2 쪽 번호: 날짜 필터가 실제로 걸리면서 2쪽 이상에서 날짜나 상태를 바꾸면 옛 쪽 번호로 요청해 결과가 있어도 빈 표가 보였다. `SalesOrderList.tsx`, `SalesQuoteList.tsx` 에서 시작일, 종료일, 상태를 바꾸면 1쪽으로 돌아간다(견적 포함은 AI 결정 행). `sales.server-contract.test.tsx` 에 화면 테스트 4개(주문, 견적 각각 날짜와 상태): 2쪽으로 간 뒤 고르면 page=0 으로 startDate, endDate 를 보낸다. 수정 전 4개 모두 `expected '1' to be '0'` 으로 실패.
2. P3 단위 훅을 `sales.labels.ts`(`'use client'`, `useSalesLabels`)로 옮기고 두 모달 import 를 절대 경로로 맞췄다. `useUomLabel.ts` 는 지웠다.
3. P3 `OrderQueryParams` 를 `Required<QueryOf<'/business/sd/orders'>>` 로 계약 생성 타입에서 끌어온다. 생성 타입의 `startDate` 를 잠깐 `start` 로 바꾸면 tsc 오류 10개가 나는 것을 확인했다.
4. P3 계약 YAML 읽기를 `src/test/contract/loadContract.ts`(`loadContract`, `declaredQueryNames`)로 빼서 `openapi.contract.test.ts` 와 `sales.contract.test.ts` 가 같이 쓴다. 견적 목록(`SdController.java:98-111`)과 매출 분석(`SdController.java:65-67`) 쿼리도 계약에 선언하고 같은 검사를 붙였다. 쿼리는 MSW `request:start` 이벤트로 모아 기본 목 응답은 그대로 둔다. 세 api 를 잠깐 `start`, `end` 로 되돌리면 3개 모두 실패.
