- 우선순위: 1 화면이 서버와 어긋나지 않는다(틀린 모양의 응답을 맞는 값처럼 쓰지 않는다), 2 실패를 숨기지 않는다

## 현상

1. api 함수는 `axios.get<ApiResponse<T>>` 의 제네릭으로 응답을 "그렇다고 치고" 쓴다. 필드가 빠지거나 타입이 달라도 화면까지 그대로 간다. 빈 칸이나 `undefined` 로 그려지고 오류는 안 보인다.
2. 목이 두 벌이다(MSW 핸들러, 서버 목 라우트). 둘 다 손으로 써서 서로, 그리고 타입과 어긋나 있어도 알 길이 없다.
3. `ApiResponse.success` 가 boolean 이라 인터셉터가 이미 걸러낸 false 를 화면이 다시 검사한다(재무 통계 3곳).

## 완료 기준

1. 영업, 구매, 생산의 화면용 읽기 응답(GET 44개, 견적 시뮬레이션 POST 1개)을 zod 로 확인한다. 틀리면 `invalidShape` AppError 로 올리고, 메시지에 첫 번째로 틀린 필드 경로를 적는다(테스트).
2. 스키마는 기존 타입에 묶는다(`z.ZodType<기존 타입>`). 타입을 바꾸면 스키마도 컴파일 오류로 같이 고치게 된다. 객체는 looseObject(모르는 필드를 지우지 않음).
3. 계약 테스트: 세 도메인의 읽기 함수를 MSW 목과 서버 목 두 곳에 대고 돌려 스키마를 지키는지 본다. 불일치는 한 번에 모아 보여준다.
4. `ApiResponse.success` 를 true 로 좁히고, 항상 참인 검사를 지운다.
5. 새 경고 없음. 테스트, 빌드, e2e 통과.

## 결정 (AI 가 정함, 사용자 2026-11-10 "끝까지 진행")

1. 판별 유니온(`success: true | false`)은 두지 않는다. 인터셉터가 false 를 오류로 바꿔서 api 함수가 받는 응답은 성공뿐이다. 원본 본문을 다루는 코드가 없어 유니온은 쓰는 곳이 없다.
2. 목과 타입이 어긋날 때: 목끼리 다르면 타입 쪽에 맞춰 목을 고친다. 두 목이 같은 방식으로 타입과 다르고 화면이 그 필드를 안 읽으면 타입을 선택 필드로 푼다. 화면이 읽는 필드가 목에 없으면 목을 고친다.
3. 상태 코드가 타입에서 유니온인 필드(견적, 주문, 발주, 공급사 상태와 분류, 가용재고 상태)는 `z.enum` 으로 확인한다. 서버가 새 코드를 보내면 형식 오류로 보인다. 모르는 상태를 조용히 그리지 않는 쪽을 골랐다(우선순위 1).
4. zod 는 클라이언트 번들에 들어간다(우선순위 3 비용). 크기는 측정하지 않았다. 성능 블록에서 `zod/mini` 전환을 본다.
