## 근거

- 견적 목록 필터: 게이트웨이 `business/controller/SdController.java:101` 설명이 `PENDING, REVIEW, APPROVAL, REJECTED, ALL`, enum `business/constants/QuotationStatus.java:13` 이 `APPROVAL`, 목록 DTO 주석 `business/dto/quotation/QuotationListItemDto.java:20` 도 `APPROVAL`. `business/service/impl/SdHttpServiceImpl.java:325` 는 status 를 바꾸지 않고 업스트림에 넘긴다. 게이트웨이 사본에서 APPROVED 를 받는다는 근거는 없다(승인 API 설명 `SdController.java:392` 는 상태 변경 결과 설명이지 필터 값이 아니다).
- 주문 상세: `SdHttpServiceImpl.java:289-292` 가 업스트림 응답을 `Object` 로 프록시해서 사본으로 실제 모양을 확정할 수는 없다. 다만 DTO 두 벌 `business/dto/sd/response/OrderCustomerDto.java:11` 과 `business/dto/order/CustomerSummaryDto.java`("고객사 ID (UUID v7)")가 같은 모양이다. customerId 는 문자열, customerCode 는 없다. 나머지 필드(`OrderDetailDto.java`, `OrderItemDto.java`, `CustomerManagerDto.java`, `SalesOrderDetailResponseDto.java`)는 이름과 타입이 화면 스키마와 같다(금액, 수량은 BigDecimal 이나 Long 이라 숫자).

## 결과

1. 견적 목록 상태 필터가 승인에서 `status=APPROVED` 를 보냈다. `constant.ts` 의 `QUOTE_STATUS_OPTIONS` 를 `APPROVAL` 로 바꿨다. 계약 `GET /business/sd/quotations` 의 status 에 enum(ALL, PENDING, REVIEW, APPROVAL, REJECTED)을 두고 `openapi.gen.ts` 를 다시 만들었다. 선택지 타입은 `SalesQuoteListType.ts` 의 `QuoteStatusFilter`(계약 enum 에서 끈다)라 APPROVED 를 다시 넣으면 tsc 가 막는다. 받는 쪽 `QuoteStatus` 는 그대로 두 형식을 받는다. 화면 글자는 공통 `status.APPROVAL`(승인, Approved)로 바뀌지 않는다. MSW 견적 목록은 행 상태를 게이트웨이 목록 값 `APPROVAL` 로 바꾸고 status 로 거른다(ALL 이나 없음은 전부). 옛 값 APPROVED 로 거르면 빈 목록이다.
2. 주문 상세 zod 스키마와 계약 `OrderDetail.customer` 가 숫자 customerId 와 customerCode 를 요구했다. 게이트웨이 모양이 오면 주문 상세가 형식 오류로 막혔다. customerId 를 문자열로 바꾸고 customerCode 를 스키마, 계약, 생성 타입에서 뺐다(looseObject 라 와도 지우지 않는다). 화면은 두 필드를 보이지 않아 화면 코드는 그대로다. 다른 필드는 바꾸지 않았다. MSW 주문 상세 고객도 같은 모양으로 바꿨다. 옛 모양 목은 기본 계약 테스트(zod, YAML 둘 다)에서 걸린다.
3. 매출 분석 상위 고객 이름(코디네이터 지시로 이 카드에 포함): 게이트웨이는 업스트림 응답을 타입 `SalesAnalyticsResponseDto` 로 받아 다시 직렬화한다(`SdHttpServiceImpl.java:67-75`, `SdController.java:63`). 그 안의 `business/dto/analytics/TopCustomerDto.java:15` 는 `customerNumber` 라 `customerCode` 는 나갈 수 없다. 화면 스키마는 `customerCode` 를 요구해서 상위 고객이 한 명이라도 있으면 실서버에서 매출 분석이 형식 오류였다. zod(`sales.schemas.ts`), 계약 `TopCustomer`, 생성 타입, MSW 매출 분석, `SalesChart.tsx` 의 고객 막대 id 를 `customerNumber` 로 바꿨다. 화면 글자는 그대로다(번호는 화면에 보이지 않는다).
4. 다른 불일치는 아래 "별도 보고". 고치지 않았다.

## 리뷰 반영

작성자를 가린 Claude 리뷰어의 P2 1개, P3 3개. 전부 반영했다.

1. P2 주문 상세 `customerId: z.string()`: 방향은 그대로 둔다. 게이트웨이가 `Object` 로 프록시해 업스트림 실제 타입은 사본으로 확인할 수 없다. `ai/decisions.md` 의 이 카드 행 이유 칸에 "실서버 주문 상세 응답 샘플로 customerId 타입 확인 필요(verified=false), 숫자로 오면 스키마를 다시 정한다"를 덧붙였다. 아래 "남긴 것"에도 적었다.
2. P3 `QuoteQueryParams.status` 를 `string` 에서 `QuoteStatusFilter` 로 좁혔다. 이제 getQuoteList 로는 APPROVED 를 보낼 수 없다(tsc 오류 1개로 확인). 그래서 옛 값을 보내는 목 테스트는 `@/lib/axiosInstance` 로 직접 부른다.
3. P3 목 견적 목록에 계약 enum 상태마다 한 행을 넣었다(QT-2026-001 APPROVAL, 002 PENDING, 003 REVIEW, 004 REJECTED). 데모에서 어느 필터를 골라도 표가 비지 않는다. 옛 값 APPROVED 주석은 "목은 빈 목록, 실서버는 QuotationStatus.from 이 예외를 던질 수 있어 미확인"으로 고쳤다. `sales.server-contract.test.tsx` 에 상태별 테스트 4개(필터마다 행이 있고 상태가 같다)를 더했다. 전체 목은 이제 4행이라 같은 파일의 ALL 기대값을 1에서 선택지 수 기준(4)으로 바꿨다. 행이 여러 개가 되면서 `sales.i18n.test.tsx` 의 견적 목록 테스트 2개가 "상세" 버튼을 여러 개 찾아 깨졌다. QT-2026-001 행 안의 버튼을 누르게 고쳤고(`rowButton`) 단언은 그대로다. 견적 상세 목은 예전처럼 어느 id 든 QT-2026-001 내용을 준다(손대지 않았다).
4. P3 형식 오류 테스트가 원인을 구분하게 했다. 매출 분석 옛 이름 테스트는 `rejects.toMatchObject({ kind: 'invalidShape' })`. 주문 상세 형식 오류 테스트 2개(숫자 customerId, 고객명 없음) ko, en 에 `getOrderDetail` 의 같은 단언을 더했다.

## 별도 보고

1. 견적 목록 행(불확실): `business/dto/sd/response/QuotationListItemDto.java:13-20` 은 managerName, quotationDate, totalAmount 가 없고 productId, quantity, uomName 이 있다. `business/dto/quotation/QuotationListItemDto.java:13-20` 은 화면과 같다. 응답은 프록시(`SdHttpServiceImpl.java:334`)라 어느 쪽인지 사본으로 못 정한다. 앞쪽이면 견적 목록이 형식 오류다.
2. 주문 상태 코드(불확실): 목록 파라미터 설명은 `IN_PRODUCTION`(`SdController.java:343`)인데 `business/dto/order/OrderSummaryDto.java:17` 주석은 `PRODUCTION`. 업스트림이 PRODUCTION 을 보내면 주문 목록과 상세의 zod enum 이 막는다.
3. 담당자 이메일 null(불확실): `business/dto/order/ManagerDto.java:15` 주석이 "목록에선 null 가능". 화면 `managerSchema`(`sales.schemas.ts:35-39`)는 문자열을 요구해 null 이 오면 주문 목록이 형식 오류다. 게이트웨이 `ApiResponse` 의 NON_NULL 은 바깥 봉투에만 걸린다.
4. 고객 등록 응답(불확실, 화면이 검증하지 않음): 계약 `CreateCustomerResponse` 는 숫자 customerId 와 customerCode 인데 `business/dto/customer/CustomerCreateResponseDto.java:13-14` 는 문자열 customerId 와 customerNumber 다. 응답은 프록시(`SdHttpServiceImpl.java:135`)다.
5. 매출 분석 실패 숨김(우선순위 2): `SalesChart.tsx` 는 `useQuery` 의 오류를 보지 않는다. 조회나 형식 검사가 실패하면 "데이터가 없습니다" 빈 상태로 보여 실패와 빈 기간이 구분되지 않는다.
