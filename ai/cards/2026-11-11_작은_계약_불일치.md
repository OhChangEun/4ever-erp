# 작은 계약 불일치

- 출처: 서버 계약 점검
- 우선순위: 1 서버와 일치(발주 반려 사유), 2 실패를 숨기지 않기(대시보드 탭 이름)
- 브랜치: fix/small
- 구현: Claude(erp-dev)

## 결정할 것

결정할 것 없음. 탭 글자는 지시대로 기존 탭 글자 모양(`발주 프로세스`)과 재고 화면 영어(`Receiving`, `Shipping`)를 따랐다.

## 근거

- 팀 백엔드 사본 `_4EVER_BE_GW/.../dashboard/service/impl/DashboardServiceImpl.java:185,189` 가 재고 담당 워크플로우에 `tabCode("IN")`, `tabCode("OUT")` 을 만든다. 같은 파일이 보내는 탭 코드는 PO, AR, QT, AP, SO, IN, OUT, ATT, LV, MES 다.
- `_4EVER_BE_GW/.../scm/mm/controller/MmController.java:530` 이 발주 반려 본문을 `PurchaseOrderRejectRequestDto` 로 받고, 이 DTO 의 필드는 `reason` 하나다(`scm/mm/dto/PurchaseOrderRejectRequestDto.java:7`).
- FE git 기록: `61546896` 이 `{ reason }` 으로 보냈고, `2bcaa8f0` 이 `{ body }` 로 바꿨다(같은 커밋에서 URL 끝에 쉼표도 들어갔다). 같은 커밋의 구매 요청 반려는 `ea32ac8d` 에서 `{ comment: body }` 로 되돌아갔지만 발주 반려는 그대로였다. 지금까지는 서버에 사유가 null 로 들어갔다.

## 결과

1. 대시보드 IN, OUT 탭. `dashboard/{ko,en}.json` 의 `workflow.tabs` 에 IN(입고 프로세스, Receiving), OUT(출고 프로세스, Shipping)을 더했다. `dashboard.utils.ts` 는 메시지 키에서 탭 목록을 만들어 코드 수정이 필요 없었다. 재고 담당이 보던 "알 수 없는 프로세스" 탭 두 개가 이름으로 보인다. 테스트 `dashboard.i18n.test.tsx` 2건(ko, en). 수정 전 2건 모두 실패했다.
2. 발주 반려 본문. `purchase.api.ts` 가 `{ reason }` 을 보낸다. 본문 타입을 생성 타입(`openapi.gen.ts` 의 이 경로 requestBody)에서 가져와, 계약이 다시 틀어지면 `tsc` 가 잡는다. 계약 `openapi/everp.yaml` 의 requestBody 필드를 `reason` 으로 고치고 `pnpm openapi` 로 생성 타입을 다시 만들었다. 목 핸들러는 `reason` 이 없으면 400 을 돌려준다. 테스트 `purchase.mutations.test.tsx` 2건(보낸 본문이 `{ reason }`, 목이 `{ body }` 를 400 으로 막음). 수정 전 2건 모두 실패했다.

## 별도 보고

1. FE `workflow.tabs` 의 `PR`(구매 프로세스) 키는 게이트웨이 대시보드가 보내지 않는다. 사본 전체에서 `"PR"` 은 `AlarmController.java:68` 의 알림 모듈 값뿐이다. 지우지 않았다.
2. 목 대시보드 핸들러(`dashboard.handlers.ts:22`)는 게이트웨이에 없는 `APPROVAL` 탭 코드를 쓴다. 손대지 않았다.

## 리뷰 반영

1. 목이 `reason` 이 문자열인지도 본다(계약은 string 필수).
2. 남긴 것: 화면에 반려 사유 입력칸이 없어 늘 빈 문자열을 보낸다(이번 전부터). 입력칸을 만들지는 화면 사양이라 별도 카드 후보.
