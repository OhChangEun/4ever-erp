# 오류를 빈 데이터로 숨기는 fallback 제거

- 출처: 리팩토링 15문제 표(옵시디언 `4ever-erp_AI_개선_계획_2026-11-09` 1주차 "오류 분리") / 아키텍처 계획 5절 5번
- 우선순위: 2 입력 보존과 실패 노출 (실패를 빈 목록으로 보여주면 1 서버와 일치도 깨진다)
- 브랜치: refac/오류_분리_fallback_제거
- 크기: 2일 (결정 반나절, 테스트와 구현 1일, 검증 반나절)

## 현상

API 호출이 실패해도 화면은 "데이터 없음"으로 보인다. 오류 상태가 보이는 자리가 43곳 있는데 한 번도 도달한 적이 없다.

1. 전역 axios 응답 인터셉터가 `API_BASE_URL` 로 시작하는 모든 실패를 200 응답으로 바꿔치기한다 (`src/lib/axiosInstance.ts:175`~`:205`). 바꿔 넣는 값은 URL 패턴별 빈 데이터다 (`src/lib/axiosInstance.ts:41` `buildFallbackData`). 끄는 스위치 `NEXT_PUBLIC_API_FALLBACK=disabled` 는 기본이 켜짐이다 (`:10`). `.env.example` 과 문서 어디에도 이 스위치가 없다.
2. 인터셉터를 전역 기본 인스턴스(`axios.interceptors`)에 등록해서, `@/lib/axiosInstance` 를 import 한 8개 모듈뿐 아니라 `'axios'` 를 직접 import 한 6개 모듈(`inventory.api.ts`, `hrm.api.ts`, `production.api.ts`, `warehouse.api.ts`, `lowStock.api.ts`, `BomDetailModal.tsx`)도 같은 영향을 받는다. 모듈 하나라도 로드되면 앱 전체가 바뀐다.
3. 알림 API 두 함수는 인터셉터와 별개로 `catch` 에서 빈 값을 돌려준다 (`src/lib/api/notification.api.ts:24` 빈 목록, `:34` `{ count: 0 }`).
4. 통계 띠를 그리는 9개 페이지가 `useQuery` 의 `isError` 를 읽지 않는다 (`src/app/(private)/sales/SalesClient.tsx:18`, `dashboard/DashboardClient.tsx`, `low-stock/page.tsx:12`, `hrm/HrmClient.tsx`, `inventory/InventoryClient.tsx`, `production/ProductionClient.tsx`, `purchase/PurchaseClient.tsx`, `finance/FinanceClient.tsx`, `warehouse/page.tsx`). `StatSection` 은 `statsData?.[period] ?? []` 라 (`src/app/components/common/StatSection.tsx:26`) 통계가 실패하면 빈 띠가 조용히 나온다. 지금은 fallback 이 0 값 통계를 만들어 주므로 "0원, 0건"으로 보인다. 이게 가장 위험한 모양이다. ERP 사용자가 매출 0원을 믿는다.
5. 서버 목이 모르는 경로는 404 를 돌려주는데 (`src/app/api/[...slug]/route.ts:1874`) 이것도 fallback 이 삼켜서 "엔드포인트가 아직 없다"는 사실이 화면에 안 보인다.

유일하게 axios 오류 모양을 읽는 소비자는 BOM 모달의 409 처리다 (`src/app/(private)/production/components/modals/BomDetailModal.tsx:53`, `axios.isAxiosError(err) && err.response?.status === 409`). 오류를 정규화하면 이 자리도 같이 바뀌어야 한다.

## 재현

`NEXT_PUBLIC_API_MOCKING=enabled` 로 개발 서버를 띄운다. MSW 핸들러는 이미 `?mockError=true` 또는 `x-mock-error: true` 헤더면 500 을 돌려준다 (`src/mocks/utils.ts:28` `shouldError`).

1. 영업 > 고객 목록에서 DevTools 네트워크 탭의 요청 URL 에 `&mockError=true` 를 붙여 다시 보내거나, `sales.handlers.ts:20` 의 `shouldError` 분기를 `true` 로 바꾼다.
2. MSW 는 `{ status: 500, success: false }` 를 500 으로 응답한다.
3. 인터셉터가 이를 `{ status: 200, success: true, data: { content: [], page } }` 로 바꾼다.
4. 화면은 `TableStatusBox type="empty"` ("고객이 없습니다") 를 보여준다. `type="error"` 분기(`SalesCustomerList.tsx:170`)는 실행되지 않는다.
5. 같은 방법으로 `sales.handlers.ts:16` 통계를 500 으로 만들면 통계 띠가 전부 0 으로 나온다.

나머지 시나리오(네트워크 끊김, 타임아웃, 401, 403, 404, 형식 오류)는 지금 MSW 유틸로는 못 만든다. 2단계에서 `src/mocks/utils.ts` 에 시나리오 스위치(헤더 `x-mock-scenario: network|timeout|401|403|404|500|shape`)를 추가해 재현한다.

## 영향 범위

- 도메인: 전부. `*.api.ts` 14개가 전역 axios 를 쓴다.
- 쿼리 키: 읽기 쿼리 41곳 전부가 처음으로 `isError` 를 받게 된다. 특정 키를 바꾸지는 않는다.
- 공통 컴포넌트: `TableStatusBox` (오류 43곳), `ModalStatusBox` (18 파일), `StatSection` (9 페이지).
- 인증 경로: 401 과 403 이 처음으로 화면까지 올라온다. 401 의 화면 전환은 결정 8(QueryCache onError 한 곳)의 별도 카드다. 이 카드는 `AppError.kind === 'unauthorized'` 를 노출하는 데까지만 한다.
- 데모: Vercel 은 MSW 가 아니라 서버 목(`src/app/api/[...slug]/route.ts`)으로 돈다. fallback 을 지워도 서버 목이 아는 경로는 그대로 성공한다. 서버 목이 모르는 경로는 "빈 목록" 대신 "오류"로 바뀐다. 이게 의도다.

## 완료 기준

1. `buildFallbackData` 와 `NEXT_PUBLIC_API_FALLBACK` 가 레포에서 0건이다 (`grep -rn`).
2. 네트워크 끊김, 타임아웃, 401, 403, 404, 409, 500, 형식 오류 8가지가 전부 `AppError` 로 reject 된다. kind 별 단위 테스트가 있고, `status` 와 원래 `message` 가 보존된다.
3. 구매 발주 목록, 구매 요청 목록, 인사 직원 목록 3개 화면에서(영업 고객과 재고 목록은 린트 1차 브랜치가 수정 중이라 뺐다) 8가지 시나리오 각각 `role="alert"` 인 오류 상태가 보이고 빈 상태는 보이지 않는다. 3개 중 1개는 MSW 통합 테스트로, 나머지는 5단계 브라우저 확인으로.
4. 알림 목록과 개수 함수는 실패 시 reject 한다. `catch` 로 빈 값을 돌려주는 자리가 0건이다.
5. 통계 띠 9개 페이지는 통계 실패 시 0 값을 보여주지 않는다. 표시 방식은 결정 질문 2 를 따른다.
6. BOM 모달의 409 처리가 `AppError` 로 동작한다 (`kind === 'conflict'`). MSW 로 409 를 돌려줘 다이얼로그가 뜨는지 확인.
7. 성공 경로는 그대로다. 기존 테스트 21개 통과, `npm run build` 통과, 데모 계정 로그인 뒤 9개 도메인 목록이 전과 같이 뜬다.
8. ESLint 경고 수가 `eslint.config.mjs` 주석의 2026-11-09 측정값을 넘지 않는다.

## 결정 질문 (게이트 1)

1. `AppError` 모양. a) `class AppError extends Error { kind; status?; cause? }` 와 `isAppError()` 가드. b) 평범한 객체 유니온 `{ kind: 'network' } | { kind: 'http'; status }`. 추천 a. `instanceof` 와 가드 둘 다 쓸 수 있고 stack 이 남아 Sentry(플랫폼 블록)에 그대로 올라간다. kind 는 `network | timeout | unauthorized | forbidden | notFound | conflict | server | invalidShape` 8종. 계획 5절의 7종에 `conflict` 를 더했다. BOM 모달이 이미 409 를 따로 보기 때문이다.
2. 통계 띠 실패 표시. a) 띠 자리에 오류 한 줄(`role="alert"`)만. 재시도 버튼은 재시도 정책 카드(queryClient 기본값)에서. b) 띠 자리에 오류 한 줄과 "다시 시도" 버튼까지 이번에. c) 지금처럼 빈 띠 유지, 별도 카드. 추천 a. 0 값이 보이는 것만 먼저 막는다. 9개 페이지를 건드리므로 재시도까지 넣으면 카드가 3일을 넘는다.
3. 오류 문구. 화면별 기존 문구("고객 목록을 불러오는 중 오류가 발생했습니다")를 어떻게 할까. a) 기존 문구 유지, 그 아래 kind 별 한 줄 추가. b) kind 별 문구로 교체. 추천 a. 43곳을 안 건드리고 `TableStatusBox` 에 `error` prop 하나만 더한다. kind 별 문구 초안은 아래 표. 문구는 사람이 정하는 항목이라 그대로 쓸지 고쳐 쓸지 답이 필요하다.

   | kind         | 문구 초안                                                   |
   | ------------ | ----------------------------------------------------------- |
   | network      | 서버에 연결할 수 없습니다. 네트워크를 확인해 주세요.        |
   | timeout      | 서버 응답이 늦습니다. 잠시 후 다시 시도해 주세요.           |
   | unauthorized | 로그인이 필요합니다.                                        |
   | forbidden    | 이 데이터를 볼 권한이 없습니다.                             |
   | notFound     | 요청한 데이터를 찾을 수 없습니다.                           |
   | conflict     | 다른 사용자가 먼저 수정했습니다. 다시 불러와 주세요.        |
   | server       | 서버 오류가 발생했습니다. 잠시 후 다시 시도해 주세요.       |
   | invalidShape | 서버 응답 형식이 예상과 다릅니다. 관리자에게 문의해 주세요. |

4. 형식 오류 판정 범위. a) 인터셉터에서 공통으로 "2xx 인데 `success === false`" 또는 "`data` 필드가 없음" 만 `invalidShape` 로. b) 결정 3(zod 를 sales, purchase, production 에)까지 이번 카드에. 추천 a. zod 는 타입 블록 카드 그대로 두고, 여기선 응답 래퍼 수준만 본다.
5. `buildFallbackData` 안의 옛 로그인 fallback(`/api/login`, `/api/me`, `/api/logout`). 호출자 `src/app/(public)/callback/callback.api.ts` 는 import 하는 곳이 없다(죽은 코드). a) 이번에 fallback 분기만 지우고 죽은 호출자는 둔다. b) `callback.api.ts`, `USER_ENDPOINTS` 3개, `auth.handlers.ts` 의 해당 핸들러까지 같이 지운다. 추천 a. 옛 SPA 파일 4개를 지우는 인증 블록 카드와 묶는 게 diff 읽기에 낫다.
6. 전역 axios 기본 인스턴스를 계속 변형할까. a) 지금처럼 `axios.interceptors` 전역 등록 유지. b) `axios.create()` 로 전용 인스턴스를 만들고 14개 모듈의 import 를 바꾼다. 추천 a. 이 카드는 오류 노출이 목적이고, 인스턴스 분리는 유지보수성 카드(우선순위 4)로 따로 뺀다. 단 `'axios'` 직접 import 6곳은 ESLint `no-restricted-imports` 로 막는 규칙만 이번에 warn 으로 추가한다(규칙 수준은 결정이라 여기 적음).
