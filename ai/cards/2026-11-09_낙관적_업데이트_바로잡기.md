## 현상

낙관적 업데이트가 있는 모달 7곳 중 6곳이 틀렸다.

1. 목록에 쓰는 5곳은 `setQueryData(xxxKeys.lists())` 로 쓴다. `setQueryData` 와 `getQueryData` 는 exact match 라 실제 화면 쿼리 `xxxKeys.list(params)` 에 닿지 않는다. 그래서 아무 일도 안 하고, 마지막 `invalidateQueries`(prefix match) 만 일한다. 고객 등록(`NewCustomerModal.tsx:90`), 자재 추가(`AddInventoryModal.tsx:88`), 창고 등록(`AddWarehouseModal.tsx:74`), 창고 수정(`ManageWarehouseModal.tsx:114`).
2. 키를 맞췄다면 더 나빴다. 캐시 모양을 틀리게 가정했다. 고객 목록 캐시는 `{ data: SalesCustomer[], pageData }` 인데 `{ data: { customers, page } }` 로 썼다. 창고 수정은 변수 `{ warehouseId, payload }` 를 목록 맨 앞에 새 행으로 끼운다(수정인데 행이 하나 늘고, 필드가 없어 빈 행).
3. 재고 이동(`InventoryMoveModal.tsx:70`)은 리터럴 키 `['inventoryDetail', queryParams]` 를 읽어 늘 `undefined` 다. 키를 맞추면 상세(객체)에 `.map` 을 불러 터진다.
4. 안전재고(`InventorySafetyStockModal.tsx:37`)는 키는 맞지만 상세 캐시를 `{ data: InventoryDetailResponse }` 로 가정해 `safetyStock` 대신 엉뚱한 `data` 필드를 붙인다.
5. 프로필 수정(`EmploymentInfo.tsx:83`)만 맞게 동작한다(단일 키, 모양 일치). `old!` non-null 단언이 있다.
6. 7곳 모두 실패해도 `onSettled` 로 무효화한다. 낙관적 업데이트라면 맞는 규칙이지만, 생성 3곳은 낙관적 업데이트가 의미가 없어 다른 도메인과 규칙이 어긋난다.
7. PR #9 결함: 부족 재고 구매 요청(`inventory.mutations.ts`)이 재고 탭 위젯 키 `lowStockItemKeys.all` 만 무효화한다. 모달은 부족 재고 페이지(`LowStockList.tsx:43`, `lowStockKeys.list(params)`)에서 열린다. 페이지 목록이 그대로다.

## 재현

1. 창고 수정 모달에서 이름을 바꾸고 저장 → 응답이 느리면(`x-mock-scenario: timeout` 아닌 지연) 목록이 옛 이름. 키를 맞춘 상태라면 빈 행이 하나 생긴다.
2. 안전재고 수정 → 재고 상세의 안전재고가 응답 전까지 옛 값.
3. 부족 재고 페이지에서 구매 요청 → 목록의 "요청됨" 표시가 안 바뀐다(네트워크 탭에 재요청 없음).

## 완료 기준

1. 공통 빌더에 `optimistic` 옵션. `setQueriesData`(prefix match)로 목록의 모든 페이지에 적용하고, 실패하면 스냅샷으로 되돌리고, 성공과 실패 모두 끝나면 무효화한다. 테스트: 두 페이지 캐시에 즉시 반영, 실패 시 원래 값, 끝나면 invalidated.
2. 생성 3곳(고객, 자재, 창고 등록)은 낙관적 업데이트를 없애고 도메인 훅으로 무효화만 한다. 모달은 성공할 때까지 열려 있으니 미리 그릴 화면이 없다.
3. 수정 4곳은 맞는 키와 맞는 모양으로 낙관적 업데이트한다.
   - 창고 수정: 모든 목록 페이지에서 그 `warehouseId` 행의 이름, 유형, 위치, 상태만 바꾼다. 행을 추가하지 않는다.
   - 안전재고: 상세의 `safetyStock`, 목록 행(같은 `itemId`)의 `safetyStock`.
   - 재고 이동: 상세의 `currentStock` 을 이동 수량만큼 줄인다(출발 창고가 상세의 창고일 때).
   - 프로필: `profileKeys.info()` 에 입력값 병합. `old!` 없이.
4. 빠진 무효화를 넣는다. 안전재고와 재고 이동은 부족 재고 3곳(재고 탭 위젯, 부족 재고 목록과 통계)도. 재고 이동은 이동 기록과 창고별 재고 토글도. 창고 등록과 수정은 재고 쪽 창고 토글(`warehouseInfoKeys`)도. 부족 재고 구매 요청은 `lowStockKeys.lists()` 를 추가.
5. 컴포넌트 안 `useMutation` 이 쓰기 기준 0건(읽기용 4곳만 남는다).
6. 기존 테스트 119개 통과, 린트 경고 666 이하, build 통과.

## 결정 질문 (게이트 1)

사용자가 "낙관적 업데이트도 진행해줘"라고 했다. 세부는 AI 가 정했다. 결정 7("토글과 상태 변경류만")을 그대로 따른다.

1. 생성은 낙관적으로 하지 않는다. 서버가 ID, 번호, 상태를 정하고, 새 행이 지금 보는 필터와 페이지에 들어갈지 모른다. 모달을 미리 닫으면 실패 시 입력이 사라진다(우선순위 2).
2. 수정은 낙관적으로 하되 변수에서 확실히 알 수 있는 필드만 바꾼다. 담당자 이름처럼 서버가 채우는 값은 건드리지 않고 무효화로 받는다.
3. 낙관적 업데이트를 쓴 mutation 은 성공과 실패 모두 끝나면 무효화한다(낙관적 값을 서버 값으로 덮어야 한다). 안 쓴 mutation 은 지금처럼 성공 때만.
4. 재고 이동은 도착 창고의 상세를 모른다(상세는 한 창고 기준). 출발 창고 상세만 줄이고 나머지는 무효화로 받는다.
