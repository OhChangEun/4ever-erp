# 목이 쓰기 결과를 따르게

- 출처: 새 버그(조정자가 2026-11-12 운영 데모를 크롬으로 확인)
- 우선순위: 1 서버와 일치(쓰기 뒤 화면이 서버 목과 어긋남), 2 실패를 숨기지 않는다(성공 토스트 뒤 화면이 그대로라 실패처럼 보임)
- 브랜치: `fix/목이_쓰기_결과를_따르게`
- 크기: 2일
- 구현: Claude(erp-dev)

## 현상

운영 데모(Vercel)는 실서버 없이 서버 목(`src/app/api/[...slug]/route.ts:18`, MSW 핸들러 어댑터)으로 돈다. 목이 쓰기 결과를 기억하지 않고, 상태 값 일부가 서버와 다르다.

1. `/purchase` 구매 요청에서 반려를 누르고 사유를 넣어 확인하면 요청은 성공하고 "반려 처리되었습니다" 토스트가 뜬다. 목록을 다시 받아도 그 행은 "대기" 그대로다. 승인도 같다. 쓰기 핸들러(`src/mocks/handlers/purchase.handlers.ts:78`, `:82`)는 `ok(null)` 만 돌려주고 목록 핸들러(`:26`)는 늘 `PENDING` 을 준다. 화면만 보면 버튼이 안 먹은 것 같다.
2. `/hrm` 급여관리. 목이 급여 상태를 `PENDING` 으로 준다(`src/mocks/handlers/hrm.handlers.ts:120`, `:148`). 게이트웨이 enum 은 `PAYROLL_PAID`, `PAYROLL_UNPAID` 둘뿐이다(`business/enums/PayrollStatus.java`, 목록 파라미터 설명 `HrmController.java:349`). 급여 상세 모달은 `PAYROLL_UNPAID` 일 때만 "지급완료 처리" 버튼을 그려서(`PayrollDetailModal.tsx:168`) 데모에서는 그 버튼이 아예 안 뜬다.
3. 같은 일이 쓰기 핸들러 전부에서 난다. 낙관적 업데이트를 하는 안전재고 수정, 재고 이동, 창고 수정은 더 눈에 띈다. 응답 전에 바뀐 값이 무효화로 다시 가져오면서 원래 값으로 돌아간다.

## 재현

1. `pnpm dev` 로 띄우고 관리자(admin)로 로그인한다. `/purchase` 구매 요청 탭에서 대기 행의 반려 → 사유 입력 → 확인. 토스트는 뜨고 행 상태는 "대기".
2. `/hrm` 급여관리 탭에서 행을 눌러 상세 모달을 연다. "지급완료 처리" 버튼이 없다.
3. 핸들러로 보면: `POST /scm-pp/mm/purchase-requisitions/pr-001/reject` 뒤 `GET /scm-pp/mm/purchase-requisitions` 의 첫 행 `statusCode` 가 `PENDING`.

## 영향 범위

- 목 한 벌(`src/mocks/handlers/*.ts`)만. 브라우저 MSW, 단위 테스트, 서버 목이 같은 핸들러를 쓴다. 화면 코드와 쿼리 키, 계약(`openapi/everp.yaml`)은 바꾸지 않는다.
- 새 파일: 상태 저장소 `src/mocks/state.ts`.
- 손대지 않는 목: `auth.handlers.ts`(프로필, 알림), `dashboard.handlers.ts`, 아직 없는 `alarm.handlers.ts`. 다른 카드가 같이 돌고 있다.
- 인증 경로: 서버 목에서는 프록시가 붙이는 `Authorization: Bearer <세션 JWT>`(`src/app/api/proxy/[...path]/route.ts:113`)를 상태를 가르는 키로 쓴다. 프록시 코드는 그대로다.

3. 저장소는 한 곳, 로그인별(서버 목은 `Authorization`, 브라우저 MSW 는 하나), 메모리, 상한 200.
4. 테스트는 공통 setup 의 `afterEach` 에서 저장소를 비운다.
5. 목 상태 값을 서버 값에 맞춘다. 화면이 비교하는 값을 목이 안 주면 고친다. `Object`, `Map` 으로 넘기는 곳은 확정하지 않는다.
6. 화면이 상태를 안 보고 버튼을 늘 보이면 고치지 않고 별도 보고. 목은 두 번째 쓰기도 성공으로 답한다.

AI 가 정한 것(`ai/decisions.md` "카드 목이 쓰기 결과를 따르게 (AI 결정)" 행):

1. 저장소 모양. `mockState(처음 상태를 만드는 함수)` 가 "요청 → 그 로그인의 상태"를 돌려준다. 도메인 핸들러 파일이 자기 상태의 타입을 선언한다. 종류와 id 로 찾는 한 통짜리 `Map<string, unknown>` 은 읽을 때 단언(`as`)이 필요해서 쓰지 않았다.
2. 새로 만든 행은 목록 맨 뒤에 붙인다. 서버의 정렬을 모르고(verified=false), 맨 앞에 넣으면 "첫 행"을 집는 기존 e2e 와 단위 테스트가 다른 행을 집는다. 새 행이 생기는 목록은 전부 1~4행이라 뒤에 붙어도 첫 페이지에 보인다.
3. 처리 뒤 상태 값. 서버 근거가 있는 것은 그 값(구매 요청 `APPROVAL`, `REJECTED`. 휴가 `APPROVED`, `REJECTED`. 급여 `PAYROLL_PAID`. 견적 `REVIEW`, `APPROVAL`. 새 주문 `READY_FOR_SHIPMENT`). 근거가 없는 것은 화면이 비교하는 값에 맞춘다(발주 `APPROVAL` → `DELIVERING`. 전표는 매입 처리 요청 뒤 `PENDING`, 완료 뒤 `PAID`. 계획 주문은 구매 요청 뒤 `PENDING`. MRP 는 `CONVERTED`. 생산 견적은 `CHECKED`). 전표를 `RESPONSE_PENDING` 으로 하지 않은 이유: 화면이 사내 사용자의 체크박스를 `PENDING` 일 때 잠근다. `RESPONSE_PENDING` 을 주면 처리 요청을 또 누를 수 있다.
4. 계획 주문의 `INITIAL`. 화면은 `INITIAL` 과 `REJECTED` 행만 고르게 하는데 목은 `INITIAL` 을 안 준다. 게이트웨이가 `Object` 로 넘겨 확인할 수 없어 목 값을 그대로 둔다. `REJECTED` 행이 있어 "자재 구매 요청" 버튼까지는 갈 수 있다(급여처럼 길이 막힌 경우가 아니다).
5. 오타와 메시지 키가 없는 값(`READT_TO_SHIP`, 출하 목록의 `PRODUCTION`)은 그대로 둔다. 처음엔 같은 목의 상세가 쓰는 값으로 고쳤는데 계약 테스트가 깨졌다. 계약이 두 값을 `const` 로 갖고 있다(목에서 계약을 만들 때 오타까지 옮겨졌다). 이 카드는 계약을 바꾸지 않으므로 목을 계약에 맞춰 되돌렸다. 화면에는 지금처럼 "알 수 없음"이 뜬다(별도 보고 3).
6. BOM 버전(`bomServerVersions`, 모듈 변수)도 로그인별 저장소로 옮긴다. 한 방문자가 충돌 재현을 눌러 올린 버전이 다른 방문자에게 409 를 내면 안 된다.
7. 상세 목은 어떤 id 로 물어도 같은 고정 본문에 id 만 바꿔 준다. 이 동작은 그대로 두고 상태와 수정한 필드만 덮는다. 새로 만든 행의 상세도 고정 본문이다(별도 보고 8).
8. 생산 견적 시뮬레이션은 상태를 바꾸지 않는다. 훅 주석은 "시뮬레이션은 가용 재고 상태를 바꾼다"지만 서버 근거가 없고, 결과 모달을 닫기만 해도 행이 잠기면 데모에서 다시 해 볼 수 없다. 확정 요청 때 `CHECKED` 로 바꾼다.
9. 계약 테스트의 형식. 쓰기를 전부 한 뒤 계약의 GET 전부를 다시 검사하는 테스트 하나로 "바뀐 응답도 계약에 맞다"를 본다.

1. 상태를 보고 숨거나 잠겨야 하는데 늘 누를 수 있는 버튼(화면 결함, 이 카드에서 안 고침).
