# 타입 4차: 남은 도메인 응답 검증과 린트 0

- 출처: 린트 3차 결정 1(서버 값 가드 36)
- 우선순위: 1(서버가 타입과 다른 값을 주면 형식 오류로 알린다), 3(첫 로드를 늘리지 않는다), 4(린트 경고 0)
- 브랜치: refac/타입\_4차\_응답\_검증

## 완료 기준

1. 가드 36개 뒤의 GET 읽기를 zod/mini 로 검증한다(타입에 묶인 스키마, 기존 방식).
2. 검증한 뒤 가드를 지운다. 가드가 응답 필드가 아닌 것을 막던 곳은 타입을 정직하게 고친다.
3. 두 목(MSW, 서버 목)이 새 스키마를 통과하고, 가드가 막던 필드를 null 로 바꾸면 그 경로가 적힌 형식 오류가 난다(계약 테스트).
4. `no-unnecessary-condition` 0, error 로. 첫 로드 예산 안.

## 결정 (AI 가 정함)

1. 결정 3(zod 는 영업, 구매, 생산만)을 15개 읽기만큼 넓힌다. `ai/decisions.md` 같은 날 행.
2. 재무, 인사, 창고는 스키마 모듈을 요청과 같이 받는다(`getParsedLazy`). 정적으로 붙이면 세 화면이 각각 약 14KB 늘었다.
3. 계약의 `EmployeeTrainingDetail.completedAt` 은 `null` 만 허용하고 있었다(코드 생성기가 목의 null 만 보고 적음). `string | null` 로 고쳤다. 같은 뜻의 교육 이력 필드는 문자열이다.

## 결과

1. 검증하는 읽기 15개: 대시보드 워크플로, 재무 고객사와 공급사 통계, 매출과 매입 전표 상세, 인사 부서 목록, 급여 상세, 교육 프로그램 상세, 근태 목록, 교육 현황, 재고 목록, 재고 상세, 품목 정보, 창고 상세, 창고 담당자. 새 스키마 파일 5개(`dashboard`, `finance`, `hrm`, `inventory`, `warehouse` 의 `*.schemas.ts`), 계약 테스트 `src/test/contract/guardedReads.contract.test.ts`(구현 전 15개 모두 실패 확인).
2. 가드를 지우지 않고 타입을 고친 곳: 워크플로 탭이 둘보다 적게 오는 경우(`tabs.at(0)`), 통계 띠의 기간 키(응답에 온 기간만 있어 `Partial`).
3. 린트: 경고 36 → 0, 남은 규칙까지 전부 error. 목 수정 없음.
4. 첫 로드 JS: 인사 +0.4, 재무 +0.3, 창고 +0.3KB. 확인: verify(앱 418), build, e2e 72 통과 2 skip, 리뷰 지적 없음.
5. 구현은 erp-dev 에이전트가 하고 계약 수정, 지연 로드, 검증, 리뷰는 메인 세션이 했다.
