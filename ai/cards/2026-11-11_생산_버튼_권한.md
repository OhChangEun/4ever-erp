# 생산 버튼 권한

- 출처: 서버 계약 점검(생산)
- 구현: Claude(erp-dev)
- 우선순위: 1 서버와 일치, 2 실패를 숨기지 않는다(누르면 403 나는 버튼)
- 브랜치: fix/roles
- 결정할 것: 게이트웨이 `@PreAuthorize` 를 기준으로 삼는 것, 숨김과 비활성 중 숨김은 AI 가 정했다. `ai/decisions.md` 2026-11-11 "카드 생산 버튼 권한 (AI 결정)" 행.

## 근거

게이트웨이 사본 `_4EVER_BE_GW/src/main/java/org/ever/_4ever_be_gw/` 에서 직접 확인했다. 역할 이름은 `policy.ts` 의 `ROLES` 와 글자까지 같다.

- `scm/pp/controller/PpController.java:325-326` POST `/scm-pp/pp/mrp/convert`, `hasAnyAuthority('PP_USER', 'PP_ADMIN', 'ALL_ADMIN')`.
- 같은 파일 `:487-488` POST `/quotations/simulate`, `:544-545` POST `/quotations/confirm`, 같은 세 역할.
- 같은 파일의 조회와 `/quotations/preview`(`:520`)에는 `@PreAuthorize` 가 없다.
- `scm/im/controller/ImController.java:454-455` POST `/scm-pp/iv/items/info`, `IM_USER, IM_ADMIN, ALL_ADMIN`.
- `scm/mm/controller/MmController.java:184-185` POST `/scm-pp/mm/stock-purchase-requisitions`, `MM_USER, MM_ADMIN, ALL_ADMIN`.
- 리뷰 뒤 추가 확인: `MmController.java:110-111` POST `/supplier`, `:334-335` POST `/purchase-requisitions/{id}/release`, `:370-371` POST `/purchase-requisitions/{id}/reject` 는 MM, ALL_ADMIN. `ImController.java:296-297` POST `/stock-transfers`, `:422-423` POST `/warehouses` 는 IM, ALL_ADMIN. 두 파일의 `@PreAuthorize` 는 이것과 위 두 줄이 전부다.
- 처음 다섯 경로는 게이트웨이에 POST 하나뿐이다. 그래서 프록시 규칙을 메서드 없이 경로 접두사로 걸어도 다른 요청을 막지 않는다.

생산 페이지는 `OPERATIONS`(ALL_ADMIN, MM, SD, IM, PP)에게 열린다(`policy.ts` 의 `/production` 영역). 그래서 MM, SD, IM 이 시뮬레이션과 계획 주문 전환 버튼을 누르면 403 이었다. 계획 주문의 자재 구매 요청(`MrpPurchaseRequestModal`)은 IM API 다음 MM API 를 불러 ALL_ADMIN 말고는 둘 중 하나에서 403 이었다.

## 결과

1. `src/lib/authz/policy.ts` 에 게이트웨이 목록을 상수로 옮겼다. `PP_PLANNING_ROLES`(ALL_ADMIN, PP), `IM_GATEWAY_ROLES`(ALL_ADMIN, IM), `MM_GATEWAY_ROLES`(ALL_ADMIN, MM), `MRP_PURCHASE_REQUEST_ROLES`(IM 과 MM 목록 교집합, 지금은 ALL_ADMIN 하나). 각 상수 주석에 게이트웨이 파일과 줄 번호를 달았다. 처음엔 API 별 이름(`ITEM_INFO_ROLES`, `STOCK_PURCHASE_REQUEST_ROLES`)이었는데 리뷰 뒤 같은 목록을 쓰는 API 가 늘어 컨트롤러 단위 이름으로 바꿨다.
2. 같은 파일 `API_RULES` 에 다섯 경로를 더했다. `API_RULES` 는 영역 표보다 먼저 보므로 운영 역할 영역보다 좁게 막힌다. 프록시는 이제 게이트웨이와 같은 역할만 통과시킨다. 같은 영역의 조회, 미리보기, 다른 쓰기 경로는 그대로다. 리뷰 뒤 숨긴 버튼의 API(supplier, warehouses, stock-transfers, purchase-requisitions 승인과 반려)는 프록시 규칙에 넣지 않았다. 앞의 셋은 같은 경로에 누구나 쓰는 GET(목록 조회)이 있고 `canAccessApi` 는 메서드를 안 본다. 승인과 반려는 경로 가운데에 id 가 있어 접두사로 못 건다.
3. 버튼은 숨긴다. 대시보드 `QuickActions` 의 `hasRole(목록, useRole())` 와 같은 방식이다. 새 문구는 없다(ko, en 그대로).
   1. `QuotationTab.tsx` 시뮬레이션 버튼: PP, ALL_ADMIN 만. 납기 확정(MPS 생성)은 시뮬레이션 결과 모달 안에만 있어 시뮬레이션을 숨기면 같이 닫힌다.
   2. `OrdersTab.tsx` 계획 주문 전환 버튼: PP, ALL_ADMIN 만.
   3. `PlannedOrdersTab.tsx` 자재 구매 요청 버튼: ALL_ADMIN 만.
4. 리뷰 반영(P2, 같은 방식): `/low-stock` 의 `LowStockList.tsx` "선택 품목 발주" 버튼(`InventoryPurchaseRequestModal` 이 `stock-purchase-requisitions` 를 부른다)을 MM, ALL_ADMIN 에게만 보인다. 처음엔 별도 보고였다.
5. 리뷰 반영(게이트웨이 다른 권한 검사 확인): 403 이 나는 역할에게 보이던 버튼이 넷 더 있었다. 확인함, 넷 다 숨겼다.
   1. `purchase/components/tabs/PurchaseRequestListTab.tsx` 승인, 반려(MmController 335, 371): MM, ALL_ADMIN 만.
   2. `purchase/components/tabs/SupplierListTab.tsx` 공급업체 등록(MmController 111): MM, ALL_ADMIN 만. 상세 모달의 수정은 게이트웨이 검사가 없어 그대로다.
   3. `warehouse/components/WarehouseList.tsx` 창고 추가(ImController 423): IM, ALL_ADMIN 만.
   4. `inventory/components/modals/InventoryDetailModal.tsx` 재고 이동(ImController 297): IM, ALL_ADMIN 만. 안전 재고 수정은 게이트웨이 검사가 없어 그대로다.
6. 체크박스와 목록 조회는 손대지 않았다. 버튼이 없는 역할도 목록과 행 체크박스는 그대로 본다. 표 구조 변경을 줄이려는 AI 결정이다(decisions.md 이 카드 행). 체크해도 보낼 버튼이 없어 요청은 나가지 않는다.
