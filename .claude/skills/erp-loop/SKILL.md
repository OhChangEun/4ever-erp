# erp-loop

유지보수용 루프다. 입력은 문제 카드 하나. 출력은 머지된 PR 과 `ai/` 아래 기록 3개(카드, 리뷰, 결정).

우선순위와 P0~P3 는 `CLAUDE.md` 의 "우선순위"와 "AI 리뷰 규칙"을 그대로 쓴다. 코드 규칙은 `ai/rules/react-typescript-antipatterns.md`. 구조는 `ARCHITECTURE.md`. 셋을 매 단계 시작 때 읽는다.

## 단계

| 단계          | 담당                | 산출물                                                                                                                    | 끝나는 조건                                                                         |
| ------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 1 기획        | `erp-plan` 에이전트 | `ai/cards/YYYY-MM-DD_<문제>.md` (템플릿 `ai/cards/README.md`)                                                             | 카드의 "결정 질문" 절까지 채움                                                      |
| 게이트 1      | 사람                | 결정 질문의 답. `ai/decisions.md` 에 한 줄씩                                                                              | 질문 0개면 자동 통과                                                                |
| 2 테스트 먼저 | `erp-dev`           | 완료 기준마다 실패하는 테스트. 리팩토링이면 현재 동작을 고정하는 characterization 테스트                                  | `npm run test:run` 에 새 테스트가 빨간불                                            |
| 3 구현        | `erp-dev`           | 브랜치 `refac/<문제>`, `fix/<문제>`, `feat/<문제>`. 측정 항목이 있으면 전후 표                                            | `npm run lint && npm run type-check && npm run test:run && npm run build` 전부 통과 |
| 4 리뷰        | `erp-review`        | `mcp__codex__codex_review` 1회. 정합성, 보안, FE 품질 3인 역할. `ai/reviews/YYYY-MM-DD_<문제>.md`                         | P0, P1 이 0 (있으면 3단계로 돌아가 고치고 다시, 최대 2회)                           |
| 게이트 2      | 사람                | PR 에서 diff 읽기. P2, P3 반영 여부. 안 고치는 건 이유와 함께 `ai/decisions.md`                                           | 승인                                                                                |
| 5 검증        | `erp-qa`            | 완료 기준을 하나씩 브라우저(claude-in-chrome)와 Vercel preview 에서 확인. 결함은 카드의 findings 절에. 측정 수치는 "후보" | 완료 기준 전부 통과. 결함 있으면 3단계로                                            |
| 게이트 3      | 사람                | 머지. 수치 후보 중 팩트대장에 올릴 것                                                                                     | 머지                                                                                |
| 6 보고        | `erp-plan`          | 카드에 결과, `ARCHITECTURE.md` 앵커 갱신, 블로그 소재 표시, 거절한 제안은 `ai/decisions.md` 거절 표에                     | 커밋 본문 끝 `리뷰: ai/reviews/<파일>`                                              |

## 호출 방법

```
/erp-loop <문제 이름>            처음부터
/erp-loop <문제 이름> --from 3   3단계부터 (카드가 이미 있을 때)
/erp-loop <문제 이름> --guard    결함 재발 방지만 (검증 단계에서 돌아온 경우)
```

문제 이름은 평문이다. 번호나 코드를 붙이지 않는다.

## 지켜야 하는 것

1. 단계를 건너뛰지 않는다. 특히 2단계(테스트 먼저)를 생략하고 3단계로 가지 않는다.
2. 카드 크기 상한은 1~3일(하루 3시간 블록). 넘을 것 같으면 1단계에서 카드를 둘로 쪼갠다.
3. 사람이 정할 것을 AI 가 정하지 않는다. 라이브러리 추가와 제거, 린트 규칙 수준, 캐시 기본값, 세션 저장 방식, 우선순위 네 줄이 충돌하는 경우, 빈 상태와 오류 문구. 전부 게이트 1 질문으로 올린다.
4. 문서만 보고 짠 코드에는 `// verified=false (provenance: <URL 또는 문서>)` 주석. 돌려 본 뒤 지운다.
5. AI 가 측정한 숫자는 카드에 "후보"로만 적는다. 팩트대장 등록은 사람이 한다.
6. 블로그 본문은 쓰지 않는다. 결정 기록, 전후 표, 분류표까지만.
7. 커밋 메시지에 AI 표기를 넣지 않는다. 타입은 `feat|fix|refac|test|chore|docs`.
8. 기존 테스트를 지우거나 약하게 만들어 통과시키지 않는다(R24). 테스트가 깨지면 원인을 카드에 적고 멈춘다.

## 전문가 3인 패널 (4단계)

Codex 한 번 호출에 역할 3개를 순서대로 돌린다. 프롬프트에 우선순위 표와 P0~P3 표, 안티패턴 규칙 문서 경로를 넣는다.

1. 정합성 심사관: mutation 뒤 무효화 범위(통계 카드 포함, 다른 도메인 침범 없음), 낙관적 락 409, 중복 제출, 늦게 온 응답, `setQueryData` 가 실제 키에 닿는지.
2. 보안 심사관: 세션 검증, 인가 규칙, CSRF, 토큰이 브라우저에 남는지, open redirect, 헤더.
3. FE 품질 심사관: 안티패턴 규칙 R01~R24, 접근성, 리렌더, 번들, 공통 컴포넌트 우선.

지적은 역할별 A, B, C 번호와 P 레벨을 붙여 `ai/reviews/` 파일 표에 적는다. 커밋 본문에는 "리뷰 반영 A1, B2" 처럼 번호만.
